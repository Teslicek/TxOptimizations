# TxOptimizations

Client-side Fabric mod for **Minecraft 26.3** (Java 25) that removes repeated per-frame work from the render thread without changing settings or what you see.

## Mod compatibility

TxOptimizations declares Sodium and Iris incompatible, along with the mods whose work it replaces (ImmediatelyFast, Entity Culling, FerriteCore, More Culling and others listed in `fabric.mod.json`); Iris cannot run without Sodium, so none of its code paths are kept. Every mixin that replaces a vanilla method outright is applied at priority 999 or lower, below the default, so other mods' injections into the calls those methods still make apply on top of the replacement, the way they would on vanilla. Without it, Mixin refuses another mod's hook into a replaced method and the game fails to start, as it did with Meteor Client's item glint, hitbox and entity visibility hooks.

## Optimizations

### Rain fog

Every frame, `AtmosphericFogEnvironment.updateRainFogState` looks up the biome and the sky light at the camera position to fade in rain fog. A spark profile showed the sky light lookup alone taking about 2.8% of the render thread. TxOptimizations looks both up once per client tick and reuses them for the other frames of that tick, as long as the camera stays in the same block of the same level. The values only feed a slowly fading fog multiplier, so the result is visually identical.

### Particle light

Every frame, each visible particle looks up the light level at its position again (`Particle.getLightCoords`). Particles only move once per tick, so at high frame rates the same lookup repeats many times per tick. TxOptimizations caches the result per particle for the current client tick and position. A light change reaches particles at most one tick (50 ms) later. Particle types that compute their own light without calling the base method are unaffected.

When a particle does look its light up again, the block position is now written into one reused mutable position instead of a new `BlockPos` (3.7 MB/s with 13,000 particles). The light lookup only reads the position, so it sees the same block.

### Vertex buffer recycling

At the end of every frame, `StagedVertexBuffer$GpuBufferPool.tryRecycleBuffers` checks every pending batch of vertex buffers to see whether the GPU is done with it. Each check is a native Vulkan call (`vkWaitSemaphores` with a zero timeout), and a spark profile showed these checks taking about 2.8% of the render thread. The batches are added in submission order and the GPU finishes submissions in that order, so TxOptimizations checks them from the oldest and stops at the first one that is still in use. Several pools (staging, vertex and index buffers for the world and the GUI) run this check every frame, and the oldest batch is usually still in use, so each pool would still make one native call per frame. While this recycle pass runs, TxOptimizations also remembers the lowest submit index the GPU reported as unfinished in the current frame and answers "not yet" for that index and every later one without asking the GPU again. It never answers "done" from memory, and vanilla's own fast path for already completed submits still runs first.

When the GPU does have to be asked, any zero-timeout completion check reads the submit semaphore's counter with `vkGetSemaphoreCounterValue` instead of calling `vkWaitSemaphores` with a zero timeout. The Vulkan spec defines both as the same question (has the counter reached this submit), so the answer is identical. The counter value is also stored as the encoder's completed submit index, so every older submit is answered by vanilla's fast path without any native call. Waits with a timeout are not touched. The result is the same set of recycled buffers with far fewer native calls. If a batch finishes in the middle of a frame or out of order, it is only reused one frame later.

### Block entity renderer lookup

Every frame, every block entity (chests, signs, heads, banners) asks `BlockEntityRenderDispatcher.getRenderer` for its renderer, which is a hash map lookup by block entity type. On a server lobby with many block entities this took about 1.7% of the render thread. TxOptimizations remembers the renderer on each block entity together with the renderer map it came from. A resource reload replaces that map, so the next lookup after a reload refreshes automatically, and a block entity's type never changes. The renderer returned is always the same one vanilla would return.

### Entity renderer lookup

Every frame, every entity asks `EntityRenderDispatcher.getRenderer` for its renderer, which runs a type switch to separate players and mannequins from other entities and then looks the renderer up by entity type in a hash map. TxOptimizations remembers the renderer on each entity together with the renderer map it came from, the same way it does for block entities. A resource reload replaces that map, so the next lookup after a reload refreshes automatically. Players and mannequins are never cached here because their renderer depends on the skin model.

Submitting an entity looks its renderer up a second time, from its render state's entity type. That renderer is now remembered on the entity type together with the renderer map it came from, so the lookup is skipped the same way; player render states still pick their renderer by skin model. In a world with 412 entities this lookup went from 1.24% and 1.56% to 0.71% and 0.50% of the render thread over two runs per build.

### Entity render states

Every frame, every visible entity got a new render state, which vanilla fills from the entity, uses to submit the entity's model, text and shadow, and then drops. For item displays, armor stands, players and villagers these states, with the item and equipment states inside them, were among the largest allocations on the render thread. Each entity now keeps the state it was last extracted into, and vanilla fills that one again. Vanilla's extraction sets every field on every extraction; the one field it only sets while a name tag is shown, the name tag attachment, is cleared first, and so is Fabric's per-state data map, which then reads the same as on a fresh state. A state is only kept for vanilla's own renderers, only in the world's entity pass (the local player is extracted a second time for the first-person view, and that extraction still gets a fresh state), and only while the entity keeps the same renderer. A test build that also extracted every entity into a fresh state and compared every field, including the nested item, equipment and shadow states, found no difference in 7.15 million extractions. In a scene with 40 armored mannequins, 41 armor stands, villagers, holograms and 140 item displays, render thread allocation fell from 1,566 to 1,232 MB/s, and over four runs per build the frame rate rose by 2 to 5% in every view.

### Sound listener updates

Every frame, `SoundEngine.updateSource` sends the camera's position and direction to the sound thread, and every send wakes that thread from sleep. At thousands of frames per second this took about 1% of the render thread. TxOptimizations skips the update when the camera has not moved or turned since the last one that was sent, and otherwise sends at most one update every 5 ms. Each frame compares against the last update actually sent, so the final position after you stop moving is always sent within 5 ms. OpenAL applies listener changes once per mixing block, which is normally longer than 5 ms, so the limit is not audible. When the sound system restarts (`loadLibrary`), the last sent update is forgotten so the listener is set again on the next frame. The camera's position and direction are compared with the last sent update before anything is built, so a frame that sends nothing no longer allocates the transform, its two direction vectors and the task that vanilla built first.

### Left-to-right text

Every piece of text drawn on screen goes through `FormattedBidiReorder.reorder`, which runs ICU's bidirectional algorithm and Arabic shaping on it, even for plain English. When the language is left-to-right and the text has no right-to-left letters, Arabic numbers or explicit direction marks, the algorithm always produces a single left-to-right run covering the whole text, and shaping changes nothing. TxOptimizations detects that case with ICU's own character direction data and builds the same single run directly. Any text with Hebrew, Arabic or direction control characters, and every right-to-left language, still goes through vanilla.

### Camera fluid

`Camera.getFluidInCamera` checks the blocks at the camera and at the four near-plane corners for water, lava and powder snow, and it is called several times per frame. TxOptimizations computes it once per frame and reuses the answer while the camera's level, position and rotation are the same. The check itself is one fluid lookup at the camera's block, then a fluid lookup and usually a block lookup at five points of the near plane. The near plane is a few hundredths of a block across, so these points almost always fall in the camera's own block, and a point in the same block as the previous one reuses that lookup. The five points are computed as plain numbers with the same sums vanilla's vectors use (the forward point, then forward plus or minus up, plus or minus left), added to the camera position and floored into one reused block position, so the check no longer creates ten vectors, a point array and five block positions per frame. The points, their order and every comparison are unchanged.

### Spare vertex buffers

At the end of every frame, the vertex buffer pools close every spare buffer that was not used in that frame, so a buffer that is needed again a frame later has to be created again. TxOptimizations keeps a spare buffer for up to 3 idle frames before closing it, and only clears its idle-frame counts when there are any to clear. Spares that get reused never reach that limit, and buffers the GPU is still using are never touched. When the HUD cache ends its offscreen frame, the pools leave their used and spare buffers as they are, and the end of the real frame handles them.

### Translation templates

Every time a translated text is resolved, `TranslatableContents.decomposeTemplate` runs a regular expression over the translation string to find `%s`, `%1$s` and `%%`. TxOptimizations parses each distinct translation string once, remembers the literal parts and argument positions, and replays them in the same order with the same argument lookups. Invalid translation strings are left to vanilla so they fail and fall back exactly as before. Up to 4096 strings are kept, and the cache is cleared when it fills up.

### HUD text layout

The F3 screen and other HUD text drawn from a plain string built every line again each frame: its visual-order sequence through the bidirectional reorder, its width for alignment and its laid-out glyphs, although most lines read the same from one frame to the next. The width of each string is now kept per string content and font, and each string content gets one shared visual-order sequence per language. Once a string has been drawn in an earlier frame, its laid-out glyphs are kept in the world text layout cache under that shared sequence, position, colors and shadow, so lines that change every frame, like the coordinates while moving, are laid out as before and never stored. These entries are dropped after 200 unused frames and on every font reload or font option change, and drawing a cached layout only reads it. In TxBench with F3 open, the lobby station rose from 8,874 to 10,556 fps (+19.0%) and from 9,643 to 10,843 fps (+12.4%) facing the other way, and the heavier template scenes by 2 to 14%; with F3 closed nothing changed.

### F3 entry checks

`DebugScreenEntryList.isCurrentlyEnabled` searches the list of enabled F3 entries one by one, and it is called for many entries every frame. TxOptimizations answers from a hash set built from that list, rebuilt whenever vanilla's own version counter for the list changes. `getCurrentlyEnabled` also made a fresh immutable copy of the list on every call, several times per frame; the copy is now kept and handed out again until that same version counter changes.

The F3 entries also formatted their value lines with `String.format` every frame, the slowest step of the overlay: the system specs entry alone took 4.5% of the render thread with F3 open. Each format call now keeps its last arguments and text and returns that text when the locale and every argument are equal and all of them are strings, numbers, booleans, characters or enums, whose formatted text depends only on their value; any other argument formats as before. With F3 open in TxBench the lobby station rose from 10,553 to 10,840 fps (+2.7%).

### Particle layers

Every frame, each particle quad is added to `QuadParticleRenderState`, which looks up the storage for the particle's layer in a hash map. The layer is a record, so every lookup hashes its fields again. Particles only ever use six constant layer objects and the map never loses an entry, so TxOptimizations remembers each layer object it has seen together with its storage and returns that storage directly. A layer it has not seen yet still goes through the map.

### Buffer builder elements

Every new `BufferBuilder` looks up up to eight vertex elements (position, color, UVs, normal, line width) by name in its vertex format, and the format's element map compares the names one by one. Vertex formats never change, so TxOptimizations resolves those eight elements once per vertex format with the vanilla lookup and reuses the result for every later `BufferBuilder` of that format, including the constructor's check that the format has a position element. The constructor passes the name straight from its name table, so the index is found by comparing that exact string object against the eight table entries, and the element is taken from the cached array at that index instead of being searched for by name. Reading the constructor's loop index directly made MixinExtras allocate an int holder for every new `BufferBuilder` (13 MB/s on minemen).

### Player skin model lookup

Every frame, `EntityRenderDispatcher.getAvatarRenderer` reads each player's skin through the player list and skin manager to choose the wide or slim player model, once for culling and once for drawing. TxOptimizations keeps the skin it read for that player during the current frame and reuses it for the second call. A skin that finishes loading is picked up on the next frame.

### Translucent sorting

Translucent geometry such as entity translucency, text, see-through name tags and glints is sorted back to front every frame. Vanilla reads the center of every quad with six bounds-checked `ByteBuffer.getFloat` calls and writes the six sorted indices per quad through an `IntConsumer` lambda. TxOptimizations reads the same floats straight from native memory when the buffer is direct and in native byte order (one bounds check for the whole range up front), computes the centers with the same arithmetic, and writes the same index values straight to the buffer's memory when it is direct and in native byte order, with one bounds check for the whole range, and through a short or int view of the buffer otherwise. The bytes written and the final buffer position are identical.

### Glow check spectator state

Entity extraction asks `Minecraft.shouldEntityAppearGlowing` for every entity every frame, and for every entity that is not glowing vanilla checks whether the local player is a spectator. TxOptimizations computes that once per frame and reuses it for the other entities.

### Frame clock

`Util.getMillis` reads the time through a native call into SDL, and vanilla called it once for every entity checked for visibility (to see whether its chunk section has faded in far enough), once for every visible section holding block entities, and every time an enchantment glint render type was prepared, every frame. Over four profiles of BedWars games these calls took 0.90 to 1.31% of the render thread. The time is now read once at the start of each frame, and those three places use that value. It is earlier than vanilla's by the time the frame had been running at that point, less than one frame, so an entity or block entity in a section that is fading in can appear one frame later, and every glint of a frame scrolls by the same time.

### Environment attribute values

Sky color, fog color and other environment attributes are read through `EnvironmentAttributeProbe$ValueProbe.get`, which blends the previous and current tick values for the frame's partial tick every time it is called, several times per frame. The blend only depends on those two values and the partial tick, so TxOptimizations remembers the last result and returns it while both values and the partial tick are unchanged.

### GPU crash checkpoints

When the GPU supports `VK_AMD_buffer_marker` or `VK_NV_device_diagnostic_checkpoints`, renderpearl writes a marker into the command buffer at every render pass so a driver crash report can name the last pass that ran. That took about 0.4% of the render thread. TxOptimizations makes renderpearl use its built-in no-op checkpoint storage, the same one it uses on GPUs without those extensions. Rendering is unchanged, but a GPU driver crash report no longer lists the last render passes.

### Particle rotation

Every camera-facing particle allocated a new rotation quaternion each frame. The quaternion is now reused, reset to identity first as the new one was.

Each particle then rolls that quaternion by its roll angle, which computed a sine and cosine for every particle every frame even though almost every particle has a roll of zero. With 13,000 particles on screen, `SingleQuadParticle.extract` took 21% of the render thread. For a roll of exactly zero, JOML's sine of half the angle is that same zero and its cosine is exactly 1, so the rotation is now computed with those two values directly, the same multiplications and additions in the same order, giving identical bits including signed zeros. Any other roll, and JOML's fast math mode, still go through `rotateZ`.

### Main target clear

Every frame cleared the main color and depth target before rendering, and the world render cleared the same target again with the fog color before drawing anything. When a world is rendered, the first clear is skipped. Screens without a world still clear as before.

### Particle corners

For every particle, vanilla rotated the four corners of the quad by the particle rotation, four quaternion rotations per particle per frame. Camera-facing particles all carry the camera rotation, so the rotated corners are the same for each of them. The rotated corners are kept while the rotation stays bit-for-bit the same, and only the per-particle scale and offset are applied, in the same order as before, so every vertex is identical. Particles with their own roll miss that cache, so a new rotation no longer goes through `Vector3f.rotate` once per corner, which works out the ten quaternion products and the normalization each time: they are worked out once per rotation, and each corner uses the same expressions JOML 1.10.9 uses, with `org.joml.Math.fma`. 100 million random rotations gave bit-for-bit the same corners, and in the scene with every particle type corner rotation went from 4.0 to 2.2% of the render thread. Each layer's particle storage is also kept by identity when the layers are built, since layers are never removed from the map and hashing a layer walks its render pipeline.

Particles with a roll of their own carry a different rotation each, so the corners are rotated again for each of them (1.48% of the render thread with 1,229 particles in a CubeCraft lobby). JOML rotates a vector with sums of products of its components, so the two opposite corners come out as the exact negatives of the first two, unless a component of the result is zero or NaN, where the sign of a zero can differ. Only the first two corners are now rotated, and the other two are their negatives when every component is a nonzero number; otherwise all four are rotated as before. Over 4,000,000 rotations, 3,463,825 of which took the negated corners, every bit matched JOML's own rotation of all four.

### Debug lines

Hitboxes and other debug lines are built with a pose that is always the identity, yet vanilla transformed every vertex position and normal through it, allocating a vector each time, and multiplied both ends of every line by the full view matrix only to read the view depth for near-plane clipping. With hitboxes shown this cost several percent of the render thread. The values are now written directly, only the depth row of the view matrix is evaluated with the same arithmetic, and an error is thrown if the pose is ever anything but the identity. When the line buffer duplicates vertices for line quads and has position, color, normal and line width, each line is written straight into the buffer in its final form (start, its copy, end) with the same encoding the buffer builder uses, leaving the end vertex for the builder to copy exactly as it would after its own calls.

Each of those vertices is now written as three 8-byte stores instead of seven separate position, color, normal and width stores, and the copy of the start vertex is written from the same values instead of being copied back out of the buffer; an offline benchmark of 4,000 lines on the game's LWJGL wrote a line in 8.6 ns instead of 10.6 ns. This only runs for vanilla's line vertex format on little-endian CPUs, whose layout is checked on every call, and otherwise the buffer builder writes the lines. The bytes are the same as the builder's apart from the fourth byte of the normal, which vanilla leaves as whatever the buffer held before and is now 0; the line shader reads the normal as three components, so that byte is never used. Over 4,000,000 random vertices, including NaN payloads, infinities and signed zeros, every other byte matched. On a CubeCraft map with 378 entities, writing the lines was 28.18% of the render thread with hitboxes shown. With this and the model quad transform above, a benchmark hub with 112 armor stands holding items, 56 villagers, 10 text displays and hitboxes shown went from 2,044 to 2,231 fps over three runs per build, faster in every run of all four views.

### Render thread memory stack

Every LWJGL call that needs scratch memory (descriptor pushes, buffer copies, mapping) fetches the thread's `MemoryStack` from a `ThreadLocal`. The render thread's ThreadLocal table is crowded, so this lookup missed its first slot and probed on almost every call, 1.7% of the render thread in the BedWars prelobby. The render thread's stack is now captured once when Minecraft starts, and `MemoryStack.stackGet` returns it directly when called from that thread. It is the same object the ThreadLocal returns, and every other thread still uses the ThreadLocal. The thread and its stack are kept in two plain fields, so the check is one comparison with the current thread.

### Empty render phase checks

Draining the frame's submit collections asked every feature render phase whether it was empty, and each check walked all of the phase's per-feature lists and batch maps, 0.3% of the render thread in the BedWars prelobby. Each phase now remembers whether anything was submitted since it was last cleared, which is the only way its lists can fill or empty.

### Per-frame allocations

Garbage collection pauses of 6 to 8 ms were the worst frames, and their frequency follows how fast the game allocates. `/txprofile`'s allocation sampling showed several sources in TxOptimizations' own code. Wrapped calls with many arguments boxed every float and int into an array on each call: the glyph writer and the baked block entity model swap in chunk meshing. They now use injectors that pass arguments without boxing. The same goes for the hooks that run every frame and always call the original method: the present thread's surface, submit and GPU wait hooks, the deferred sky, the outline scissor, the transient command buffer end and the vertex buffer pool's spare list now call it directly instead of through a wrapper that allocated an argument array on each call. Each render pass gets a number, and a pipeline records the number of the last pass that checked its color targets, so the check still runs once per pipeline per pass without a set that was filled and cleared in every pass. Each pipeline now keeps its uniform names and binding slots in two small arrays, built once in the map's own order from its fixed uniform map, so binding a pipeline walks the arrays instead of every slot of the hash map (1.9% of the render thread in the BedWars prelobby). The names come from shader reflection as new strings while the game passes string constants, so they are stored interned: a uniform's slot is found by comparing references along the array, then by content for names that are not constants, which gives the slot the map held for that name. Binding a vertex buffer writes the buffer and offset straight to stack memory instead of wrapping each in a new `LongBuffer`. The driver receives the same values in every case. Binding a texture for a draw built a new texture-and-sampler record every time the bound texture changed (9.2 MB/s with entities on screen); each cached texture list now builds those records once and the draw binds them directly, with the same equality check deciding whether the backend is told. A cube-shaped collision or outline shape built a new coordinate list each time its minimum, maximum or bounds were read, six per `bounds()` call (7.2 MB/s from entity shadows); it now divides the index by its size directly, the same `index / size` the list computed. Each feature group's debug label was a new lambda per group per frame; the feature type is now its own label supplier with the same name. The terrain draw lists are sized to their known length instead of growing from empty every frame, a HUD element's bounds are worked out once instead of twice while the HUD cache records it, and reading the GPU's submit counter writes into a direct buffer instead of pinning a Java array for the native call on every poll.

A wrapped call only allocates its argument array when the wrapper passes the call on, so the wrappers that run per entity or per particle and always or usually pass it on now take the value or make the call directly: the name tag and score text reuse receive the component vanilla just built, the per-frame player skin lookup calls `getSkin` itself on the first lookup of a frame, and the particle air check calls vanilla's collision itself for boxes that are not all air. Each sees the same value or makes the same call with the same arguments, and the score text wrapper's arrays are gone from the allocation profile.


Drawing a vertex through a pose matrix with vanilla's `VertexConsumer.addVertex(pose, x, y, z)` allocated a new vector for every vertex, which is how hitbox points, the fire on burning entities and End crystal beams are drawn. The buffer builder now transforms the position itself for JOML's own `Matrix4f`, along the same identity, translation and general paths JOML 1.10.9's `transformPosition` takes, and passes the result to the same `addVertex(x, y, z)`; any other matrix class keeps vanilla's call. The particle collision check worked on a new box widened by the particle's movement for every particle and tick; it now works out the same bounds directly, the way `AABB.expandTowards` and the box constructor do. A test build that compared both with vanilla's calls bit for bit found no difference in 9 million vertices and 2 million particle moves. In a world with 412 entities and about 13,500 particles the render thread allocated 528 and 529 KB per frame instead of 553 and 550 over two runs per build.

Every item display entity got a new render state every frame, and with it a new item render state that built all of its layers again, each layer with its own matrix and tint list (about 120 MB/s in a CubeCraft lobby full of item displays). Each item display now keeps one item render state and its render state uses it: right before vanilla fills it, the display's own state is put in, and vanilla clears it and asks it for new layers, which reuses the layers it already has. Vanilla reuses item render states the same way for the GUI and for held items. A test build that also filled a fresh item render state for every item display and compared every field of both, and of every layer including Fabric's, found no difference in 8 million item display extractions with 7.7 million layers, in a benchmark scene of about 200 item displays of 20 kinds (dyed leather, potions, compasses, clocks, heads, shields, banners, chests, enchanted items and others). There the render thread allocated 166 KB per frame instead of 216 over two runs per build.

Shelves did the same: every frame each shelf slot with an item got a new item render state, with its layers, matrices and tint lists. Each shelf block entity now keeps one item render state per slot and hands it to vanilla in place of the new one; vanilla clears it and fills it again, reusing its layers, exactly as for item displays. Empty slots are still left out of the shelf's render state. In a TxBench scene with 600 shelves holding three items each, the shelf allocation samples went from 86 to 0, and over four interleaved runs the frame rate went from 661 to 715 fps and the render thread from 1,509 to 1,396 µs per frame, with screenshots inside the scene's run-to-run variation.

The GUI renderer sorts its elements every frame by scissor area, pipeline and texture with a chain of `Comparator.comparing` calls over methods that return `int`, so every comparison boxed up to six sort keys into new `Integer` objects (about 20 MB/s in a crafting table screen). The sort now uses a comparator that compares the same keys in the same order with `Integer.compare`, which is what `Integer.compareTo` does, with missing scissor areas and textures first as before, so the stable sort puts every element in the same place. It is only used in place of vanilla's own comparator. A test build that ran both comparators on every comparison found no difference in more than 200,000 comparisons.

The texture's sort key is the texture setup record's hash code, which the generated record code worked out again, through a chain of method handles, every time two elements were compared. A texture setup never changes, so its hash code is now computed once with the record's own formula and kept in the record. A test build matched the hash the JDK generates for the record in 2.6 million calls, and with 26 effects on the player the frame rate went from 10,710 and 10,868 to 10,830 and 10,945 fps over two runs per build.
### Packed gizmo lines

With hitboxes shown, every entity's box became 8 corner `Vec3`s and 12 `Line` records each frame, plus the list storage for them, about 35 MB/s in the BedWars prelobby. Gizmo groups now keep their lines as plain numbers (start and end coordinates, color and width), a box is kept as one entry (its two opposite corners, its four colors and its width) instead of 12 lines, and the line renderer reads those numbers. For a box it converts each of the 8 corners to camera space and works out its depth once, then emits the 12 edges in vanilla's order from those corners, where every edge used to convert and project both of its ends; 300,000 random boxes and cameras gave bit-identical edge positions, depths and colors. The coordinates are the same doubles the `Vec3`s held, in the same order. Anything that still reads the list as `Line` objects gets them built on access. The two gizmo collections that `LevelRenderer` rebuilt every frame are now cleared and refilled instead, since the previous frame's collections are dropped at that point and were already drawn, so the line arrays keep their capacity and stop being reallocated. Each line written straight into a line buffer reserved space twice, once for the copy of the previous line's end vertex that line buffers add and once for the new line. When the buffer already has room for both, it is now one reservation with the same copy and the same bytes, vertex count and last-vertex pointer; otherwise it goes through the two separate steps as before, so the buffer grows exactly as it did. Emitting the gizmos took 4.14% of the render thread in a CubeCraft lobby with 450 entities, and a box added its 12 edges one at a time, each looking up its group and checking the list's capacity. A box now adds all 12 edges in one step, with the same coordinates, colors and widths in the same order. Its edges always share a group, because the colored corner edges keep the box color's alpha; a box whose edges did not would throw. In profiles of a benchmark hub with hitboxes shown, emitting the gizmos went from 2.14% to 1.59% of the render thread's samples on average, lower in every view.

Writing the box lines was the largest single cost of a CubeCraft lobby frame with hitboxes shown, 131 µs of an 890 µs frame with 467 entities loaded. A box whose coordinates are finite and whose 8 corners all lie in front of the near limit has no edge that gets cut or dropped, so its 12 edges are now written with one reservation instead of 12. The position words of its 4 x and y pairs and its 2 z values are packed once. Each edge runs along one axis, so its other two normal components are exactly zero, and the 6 normal directions are packed once per box instead of once per edge. The vertices go out in the order vanilla's buffer writes them one at a time: each end of an edge followed by its copy, with the last end's copy left for the buffer to add as before. A box that reaches behind the near limit still goes through the per-edge path. Over 3,000,000 random boxes, including flat ones, huge and tiny coordinates, clamped normals and random corner colors, the bytes matched the per-edge path exactly. In an offline benchmark of 300 entities' hitboxes, eye boxes and view arrows, with the caches flushed before every frame, building the lines took 33.7 µs instead of 49.4 µs.

### Repeated binds

Binding a pipeline on a render pass validated its attachments, recorded a pipeline bind, forgot every uniform and then set all of them again, even when that same pipeline was already bound on the pass. Vertex and index buffers were also bound again through a native call before every draw that used the buffer already bound. Binding the pipeline, vertex buffer slice or index buffer and type that is already bound on the pass is now skipped, unless the buffer has been closed so vanilla's error still fires. Setting a uniform to a value equal to the one the pass already holds for that name is skipped too, and for textures the check runs before the texture and sampler pair is allocated (5 to 6 MB/s of allocation at a CubeCraft spawn). Vanilla sets the projection, fog, globals and lighting uniforms again before every draw, and each set marked the descriptors dirty, so the next draw pushed all of them to the driver again (`setUniform` and `pushDescriptors` together took 4% of the render thread at a BedWars spawn). The backend slot already holds that value, because each pipeline change sets every stored uniform on the new pipeline's slots, and no other code writes those slots or pushes descriptors. Vulkan keeps the bound pipeline, its pushed descriptors, push constants and buffer bindings, so every draw sees the same state as before. Setting a uniform stores it with one map write and compares the value the map held before, instead of looking it up first and then writing, and the binding slot is read from the pipeline's own slot map instead of through its read-only wrapper. These checks are written into the render pass's own uniform, vertex buffer and index buffer setters, with vanilla's checks and order unchanged, instead of cancellable hooks in front of them: a cancellable hook allocates a callback object on every call, which was 13.6 MB/s of the render thread's allocation on minemen and part of what filled the young generation every 3.5 seconds (each young collection paused for about 10 ms).

### Clears on load

Every frame cleared the world target, the depth before the held item and the depth before the GUI with separate clear commands, each followed by a barrier that drains the whole GPU, and then started a render pass on the same target that loaded the cleared contents. A clear is now held back and folded into the next render pass on that texture as a clear on load when the pass covers the whole texture, which needs neither the separate command nor the barrier. Buffer uploads and timestamps may pass a held clear because they never touch the image. Any other command, or a pass that does not cover the texture, records the held clear first exactly as before.

### Upload barriers

The Vulkan backend follows every buffer upload with a barrier that makes the whole GPU finish all earlier work before anything else may start. Several uniform uploads happen back to back each frame (global settings, projection matrices, lighting), so the GPU drained once per upload. Consecutive uploads and buffer-to-buffer copies to separate buffer ranges now share a single barrier (a copy also waits when its source or destination overlaps a range still waiting; the waiting ranges never overlap each other, so they are kept sorted by buffer and start and each check is a binary search instead of a walk over every range, which grew with the square of the copies in a chunk upload), which is recorded before the next command of any other kind, before an upload that overlaps one still waiting for its barrier, and before the command buffer ends. Timestamp queries do not trigger it.

### World text layout

Name tags, holograms and other text in the world were laid out again every frame: each character looked up its glyph, built a positioned glyph instance and updated the text bounds. Components cache their visual-order sequence, so text the server has not changed arrives as the same sequence object every frame. The laid-out text is now kept per sequence object, position, colors, shadow and outline, and drawn again from the cache. Text with obfuscated characters or with player head and atlas sprite glyphs is never cached, unused layouts are dropped after 200 frames, and everything is dropped when fonts reload or font options change. Drawing a laid-out text only reads it, so the cached copy draws exactly like a fresh one. Name tags also measured the width of their component every frame to center it, one glyph lookup per character. The width of a vanilla mutable component is now kept per component object and font next to the layouts, dropped with them after 200 unused frames and on every font reload or font option change. Such a component keeps the visual-order text it was first drawn with, so the cached width always belongs to the text that is drawn; any other kind of component is measured every frame as before.

### Direct vertex writes

Vanilla writes every glyph, particle, entity model cube, item quad and entity shadow one vertex at a time through the buffer builder: each vertex checks the previous one, reserves its own space and then sets its position, color, UVs, light and normal one element at a time, and glyph, particle, item and shadow positions each go through a new vector. Without Sodium, `putBakedQuad` alone took 5.6% of the render thread in an entity-heavy benchmark scene and glyphs 2.3% in the busiest one. When the vertex buffer uses exactly the format being written, TxOptimizations reserves the space for the whole glyph, text background or underline, cube, item quad, shadow quad or particle layer at once and writes the same bytes straight into it. The reservation makes the same checks the first vertex would (the builder is still building, the previous vertex is complete, the buffer is not a line buffer that duplicates vertices, the vertex limit is not reached), updates the vertex count and last vertex pointer the way the builder does, and is only taken when the vertices fit into the memory the builder already has, so the buffer grows at exactly the same points as before; otherwise the vanilla path runs. Item and block model quads are written in vanilla's entity and block formats on any thread, world text in vanilla's lit text format, and see-through text (name tags and text displays seen through walls) and GUI text in vanilla's position, UV and color format, where the light is dropped as vanilla drops it for that format. Shadows are written in vanilla's entity format with the overlay, full light and upward normal vanilla passes for every shadow vertex. Positions are worked out with JOML's own formulas, described below. A comparison against vanilla's builder over random matrices, quads, glyphs, particle layers and buffers too small to hold them matched every byte, vertex count, last vertex pointer and buffer capacity (NaN positions compare as NaN, since the JIT may produce either NaN sign in vanilla too). Buffers with any other format, subclasses of the buffer builder, and cubes drawn off the render thread keep vanilla's per-vertex path.

Item and block model quads are written as four explicit vertices instead of a loop over the vertex index. Vanilla's baked quad and quad instance return a vertex's position, UV, color and light through a switch on that index, four switches per vertex; with constant indices they reduce to plain field reads. Writing an item quad took 11 ns instead of 15 ns in an offline benchmark on the real classes, and 8.4 million vertices of random quads, colors, lights, overlays, light emission and matrices matched vanilla's bytes in both formats.

Each item and block model quad also allocated a new vector for its transformed positions, and the JIT did not remove it: in a profile of the busiest benchmark station these vectors were the largest source of render thread allocations, about 105 MB/s by the profiler's allocation sampling. No vector is used at all now.

None of these writers call JOML for each vertex any more. JOML's position transform returns the position unchanged for a matrix it flags as identity, adds the translation for one it flags as translation only, and otherwise evaluates `m00 * x + (m10 * y + (m20 * z + m30))` per component through its `Math.fma` helper, which multiplies and then adds unless the `joml.useMathFma` option is set. Every writer takes the same three paths on the same flags with the same helper, so the result is the same in either mode. Item and block model quads and model cubes with hidden faces read the matrix through its own class instead of JOML's matrix and vector interfaces: on a CubeCraft map full of item displays and shelves, JOML's `Vector3f.mulPosition` was 18.38% of the render thread on its own, because the JIT did not inline those interface calls that deep into item writing. Glyphs and shadows also share the inner sums between corners: the four corners of a glyph have one z, so its z terms are worked out once per glyph, and a shadow quad has one y and two z values, so the y and z terms are worked out once for its near edge and once for its far edge. Over 8,000,000 vertices each for glyphs, shadows and model quads under identity, translation, rotated, scaled and arbitrary matrices, the shadows and model quads also with NaN, infinities, signed zeros and extreme values, every position matched JOML 1.10.9's (NaN positions compare as NaN). Over four profiles of BedWars games, preparing the shadows took 0.06 to 0.99% of the render thread before this change.

### Entity vertex words

Every vertex in vanilla's entity format (entity models, items, shadows) was written with nine stores: three floats for the position, the color, two floats for the texture coordinates, the overlay and light pair, and the normal. The position's x and y, its z and the color, and the two texture coordinates are now each packed into one 64-bit word in the CPU's byte order, so the same 36 bytes land in the same places with six stores. Screenshots of 170 item displays differed from the previous build in exactly the same pixels as two runs of the same build (moving clouds), and in a scene with item displays, held items and armored crowds the frame rate rose by 3 to 4% in the hub and item views over three runs per build, with the other views unchanged.

### Item quad runs

An item is drawn quad by quad, and every quad picked its normal by comparing the pose's normal matrix with the one picked last and reserved its four vertices on its own. All quads of one item share one pose, and consecutive quads with the same render type go to the same vertex builder, so the normal matrix is now picked once per item and each such run of quads reserves its vertices in one step. Every quad is then written with the same positions, colors, light and normals as before, in the same order. Reserving a run leaves the builder with the same vertex count, last vertex and write position as reserving its quads one at a time, and a run is only reserved when it fits in the memory the builder already has; otherwise its quads go one by one as before, so the buffer still grows at the same points. A test build that also computed every normal of a run without the cache matched all of them in 634 million quads, and screenshots of 170 item displays differed from the previous build no more than two runs of the same build differ (moving clouds). In a scene with 140 item displays, held items and armored crowds the frame rate rose by 2 to 7% in every view over three runs per build.

### Attribute lookups

Every attribute read, such as an entity's scale or name tag distance each frame, looked the attribute up with `computeIfAbsent` and a freshly allocated lookup function. Attribute instances are never removed from an entity's attribute map, so the lookup now reads the map first and only falls back to vanilla's `computeIfAbsent` with the same creation function when the attribute is not there yet.

### Descriptor pushes

Every draw with a changed uniform pushed the pass's whole descriptor set to the driver, and uniforms are set again for most draws even when they hold the same buffers and textures as before. Each render pass now remembers the values and pipeline layout of its last push and skips a push whose values and layout are identical. Vulkan keeps pushed descriptors for the same pipeline layout, so every draw reads the same descriptors as before. A new render pass always pushes.

### Entity shadow blocks

Every entity with a shadow checked the blocks under it every frame: the block below, the light level, whether the block below has a full collision shape and its shape. These answers are now kept per block position for the current client tick and shared by all entities, then dropped at the next tick or level change. The shadow's strength and position are still computed every frame from the entity and the camera; a block or light change under a shadow shows up to one tick (50 ms) later.

### Map colors

When a map's contents change, every one of its 16384 pixels was converted from its packed color byte to a color by looking up the map color and scaling it by the brightness. Map colors and brightness levels are fixed, so the 256 possible results are computed once with the same vanilla function and looked up per pixel. Servers that update maps in item frames often, like leaderboards, pay this on every update.

### Hitbox cuboids

Each hitbox or debug cuboid created 24 corner vectors every frame for its 12 edges and 24 more when filled, although a box has 8 corners. The edges and faces now share the 8 corner vectors, which are immutable, so the same lines and quads are emitted with fewer allocations.

Vanilla never culls item, block and text displays against the view unless the server gives them a culling size, so with hitboxes on every display in range drew its hitbox each frame, even behind the camera: a point, a 2-block view arrow and a box with zero size. When the hitbox batch writes an entity's boxes, points and arrows, the box around all of them is now tested once against the clip volume of the frame (the level projection the GPU draws with, including view bobbing and the hurt tilt, times the camera rotation), widened by 16 pixels on every side for line widths and point sizes, with arrows widened by the 1.5 blocks their heads can reach; when that box is completely outside, none of the entity's hitbox is written, since the GPU would have clipped all of it. Vanilla only draws the hitboxes of other entities after testing their culling box against the view, so one test per entity costs a quarter of the earlier test per box, point and arrow, and parts of an entity that stay outside the volume while the rest is in view are clipped by the GPU as before. A box whose corners are the same point is not written either: all of its 12 edges have zero length, and the line shader's direction for a zero-length line is not a number, so the GPU discards them. In the 360-display TxBench scene with hitboxes on, the two views rose from 2,769 to 3,218 fps (+16.2%) and from 2,676 to 3,055 (+14.2%), and the screenshots matched the old jar pixel for pixel.

### Feature renderer list

Preparing each frame walked the list of feature renderers through a freshly built Guava filter that skips empty slots, three times per frame preparation. The filtered list only changes when a renderer is registered, so it is built once at registration and reused.

### Entity visibility reuse

With entity hitboxes shown (F3+B), the hitbox renderer runs the same visibility check for every entity that entity extraction already ran earlier in the frame. Each entity remembers its result for the frame, and a second check with the same frustum, camera position, partial tick and fade setting reuses it. Any call with different inputs computes normally. The check is applied before other mods' mixins, and its section check, `LevelRenderer.isSectionCompiledAndVisible`, stays inside `isEntityVisible`, so mods that change that check, such as Meteor Client forcing entities to render, still apply.

### Block outline edges

The outline around the targeted block walks the block shape's voxel grid every frame to find its edges, which took about 2% of the render thread on complex shapes. The edges of the last 8 shapes are kept and replayed in the same order, so the outline is identical. Block shapes are immutable and shared, so a new shape object is simply recomputed.

### Resource pack zips

Zip resource packs, including the ones servers send, are read through an index of the zip's entry names built once per pack and kept sorted, so listing a folder (all textures, all models) is a binary search for its range instead of a scan of every entry in the zip, and looking up a single file asks the zip for that entry directly. Overlay folders are searched in the same order as vanilla, and a pack whose zip cannot be opened is logged and treated as empty, as vanilla does.

### Server switches

While a server reconfigures the connection (the screen shown when a network moves you between servers), frames are not rendered for up to 5 seconds, so the game does not spend the GPU and CPU on that screen. Rendering resumes as soon as the world loads, an overlay such as a resource reload appears, or the 5 seconds run out.

### Loading screens

The resource reload overlay is not drawn: while a reload runs you keep seeing the screen behind it (the title screen or the current menu, or the world in game), and as soon as the reload finishes it is completed and the overlay removed, without the fade-out. The world loading screen is not drawn once a world exists. On the first world load after starting the game, the window keeps showing the last frame while that screen is up instead of new ones: frames are still rendered, so the chunks around you keep building and the screen closes when vanilla's would, but they are not copied to the window or presented. Without that, the first join showed black frames, because the world had nothing to draw before your position and chunks arrived. Once a world frame has been shown, later joins and dimension changes present every frame as before. The title screen skips its fade-in. These change what is shown while loading, not how long the loading itself takes.

### FPS counter

TxOptimizations draws its own FPS counter in the top left corner (`123 FPS`, white, no shadow, at 2,2), hidden while the F3 screen is open or the HUD is hidden. `K` toggles it (rebindable under Options > Controls > TxOptimizations), and the choice is saved in `config/txoptimizations.json`. The file is only written when it is missing or the setting changes, never on every start, and each write goes to a temporary file that is flushed to disk and then renamed over the old one, so a system crash or power loss leaves either the old or the new file instead of a file of zeros. A file that cannot be read stops the game with its path and contents. The number is the average frame rate over the last 0.5 seconds and updates every 0.5 seconds. It only counts frames, and the text is rebuilt only when the number changes, so drawing it skips translating and laying out the text again every frame.

### Baked block entities

Chests, ender chests, shulker boxes, bells, skulls, banner poles, decorated pots, copper golem statues and cushions are baked into the chunk mesh like normal blocks instead of being drawn again every frame. They switch back to per-frame rendering only while they move: a chest or shulker box while its lid is open, a bell while it swings, a decorated pot while it wobbles, an animated dragon or piglin head. Banner flags keep waving because only the pole and bar are baked. Player heads and decorated pots with sherds stay per-frame, and a named cushion only draws its name tag per frame. In a server lobby profile this cut block entity rendering from about 4.1% to 0.35% of the render thread.

Block entities with nothing to draw are skipped: signs without text, beacons without a beam, campfires and shelves without items and lecterns without a book. The answer is remembered on each block entity for the current client tick, so a sign that gains text shows it at most one tick later. Sign text facing away from the camera is not drawn.

Every frame, each sign measured the width of each of its four lines to center it, one glyph lookup per character (13% of the render thread with 400 signs in view). A sign keeps the lines it was split into until its text changes, so the width is now kept per line object and font next to the text layouts, dropped with them after 200 unused frames and on every font reload or font option change. In a TxBench scene with 400 four-line signs, fps rose from 1,430 and 1,424 to 1,582 and 1,557, and the signs matched the old jar pixel for pixel.

### Atlases and batching

- Font atlas: font glyph textures are 1024x1024 instead of 256x256, so text spans far fewer textures and needs fewer texture switches and draw calls.
- Map atlas: map images are packed into shared 2048x2048 textures, so walls of maps in item frames draw in a few calls instead of one per map.
- Glyph vertex builder: consecutive glyphs of the same render type reuse the same vertex builder instead of looking it up for every glyph.
- Empty enchantment iteration: running an enchantment effect over an item with no enchantments wrapped the empty enchantment map in an unmodifiable set and two iterators before finding nothing to visit. Humanoid renderers work out a crossbow charge time this way for every humanoid and armor stand every frame, even with nothing in hand (0.8% of the render thread with 334 armor stands). An item with no enchantments now loops over a shared empty set, which visits the same nothing without allocating.
- Gizmo collector: every gizmo looked up the thread's gizmo collector in a `ThreadLocal`, which kept missing its first slot (up to 0.8% of the render thread with hitboxes shown). The render thread's collector now lives in a plain field that replaces the `ThreadLocal` for that thread: every read and write of the collector goes through it, starting empty like the `ThreadLocal`, and any other thread reads and writes the `ThreadLocal` as before.
- Leash holder: drawing an entity that can be leashed and has leash data looked up `level.getEntity` with the delayed holder id on every visibility check and render state, even when that id was 0 and the result was never used (up to 0.8% of the render thread with many leashable mobs). The render side now skips that lookup when there is no delayed holder and otherwise does the same lookup and hand-over as vanilla. Nothing else overrides `getLeashHolder`.
- Item vertex builder: within one item, consecutive quads of the same render type reuse the vertex builder the previous quad got, when that render type merges consecutive geometry, which is exactly the builder vanilla's lookup returns again (the item quad loop was 3% of the render thread with 334 armor stands at a CubeCraft lobby). Whether the render type merges consecutive geometry is read once when its builder is looked up instead of for every quad (0.2% of the render thread without Sodium); it only depends on the pipeline's primitive topology, which never changes.
- Animated item atlas: animated item icons in the GUI share one atlas that is cleared once per frame instead of slot by slot. This now starts with the first animated item instead of the third: vanilla clears a slot by creating a texture view of the atlas and of its depth texture, opening a render pass for them and destroying both views afterwards, for every animated item in every frame, which with one or two animated items in a crafting table screen woke the background thread that destroys GPU resources in every frame (1.6% of the render thread). The shared atlas is cleared with one plain image clear and draws each item into its slot the same way.
- Scissor state equality: vanilla merges draws of the same prepared render type inside groups it marks as reorderable, but `RenderType.prepare` copies the scissor state every time and `ScissorState` has no value equality, so two prepared render types never compare equal and the merge almost never happens. Comparing scissor states by value lets that vanilla merge work, which cuts draw calls. Strictly ordered groups are untouched.

When a loaded resource pack overrides the `core/text` shader, the font atlas stays at 256x256 unless the pack lists `font_atlas_resizing` under `compatible_features` in an `immediatelyfast` metadata section, and the map atlas is switched off when the pack lists `map_atlas_generation` under `incompatible_features`. Server resource packs with custom text shaders therefore look the same as in vanilla.

### HUD cache

The HUD is drawn into an offscreen framebuffer at up to 60 frames per second (20 while a screen is open), and every frame only blends that cached image over the world. Each HUD frame is spread over 3 render frames: HUD layers are split into 3 groups of roughly equal measured cost, and each frame redraws one group, so no single frame pays for the whole HUD. Animations inside cached layers advance by the summed frame time of the cycle. Layers whose blending reads the color underneath them, like the crosshair, switch to being drawn every frame the first time they appear, and so does anything drawn outside a registered HUD layer, including the FPS counter. Resizing the window, opening or closing a screen or hiding the HUD redraws the HUD directly for two cached frames so nothing shows stale. The cached image is blended over the world only inside up to 32 non-overlapping rectangles covering the bounds of everything drawn into it, padded by 2 GUI pixels, instead of over the whole screen, so the GPU blends the areas around the hotbar, chat, scoreboard and other HUD parts instead of every pixel. Text and blits only lack bounds when they are empty or their scissor clips them away completely, so they add no area; counting them as the whole screen made the blend cover every pixel on servers whose HUD clips text, which in a server lobby was 2.07 million fragments per frame.

A HUD layer that adds a picture-in-picture element, such as Xaero's Minimap, is not cached: the element renders into its own texture while it is prepared, which the cached passes spread over several frames could not do every frame, so the minimap flickered or was not drawn. The whole layer is drawn every frame in the normal GUI pass, in its original order, as without the cache. The offscreen HUD frame runs the GUI renderer's prepare, upload, draw and end-of-frame steps directly instead of its `render` method, so other mods' hooks on the start and end of every GUI render, such as Meteor Client's HUD, which also clears the main framebuffer's depth (the offscreen frame has none), run once per frame in the normal GUI pass as they do without the cache. Xaero's Minimap hooks of the same kind are skipped while the offscreen frame is drawn as well.

### Display culling

Vanilla only culls an item or text display against the view when the server gives it a culling width and height, which most servers leave at zero, so every item display within its view range was built and drawn every frame, even behind the camera. When an item display submits its item, the item's model bounding box (the extents vanilla computes for the item, after its item and local transforms) is now put through the display's final pose and tested against the clip volume of that frame: the level projection the GPU draws with, including view bobbing and the hurt tilt, times the camera rotation. An item whose box lies completely outside that volume is not submitted, since the GPU would have clipped every one of its vertices. The display's name tag, shadow and hitbox still go through vanilla. Items with Fabric mesh quads, items without extents and items drawn by another mod's special renderer are always submitted. In a TxBench scene with 240 item displays around the camera, one view rose from 4,584 and 4,778 fps to 6,826 fps and the other from 4,775 and 4,914 to 6,594, and below the sky the screenshot matched an old-jar run pixel for pixel.

The test transformed each of the 8 corners of an item display's box with JOML's position transform, 12 multiply-adds per corner (`Vector3f.mulPositionGeneric` was 2.1% of the render thread in a CubeCraft lobby profile with 409 entities). Corners that share a z or y value share the inner part of that sum, so the corners are now worked out with the model cube writer's corner code, which uses the same fused multiply-adds in the same order and the same identity and translation shortcuts as JOML; 8 million corners of random boxes and transforms matched JOML bit for bit, so the same items are culled.

Text displays, used for holograms and leaderboards on servers, are culled the same way. Their glyphs can come from server fonts with images taller than a line, so line metrics cannot bound them; instead each line's laid-out text is looked up in the world text layout cache under the exact key the text renderer will use, and its glyph bounds, which include shadows, italics, underlines and strikethroughs, are widened by 2 text pixels for the second copy that bold text draws. Together with the background rectangle they are put through the display's final pose and tested against the same clip volume. A line whose layout is not cached yet, such as on the first frame a text is shown, is drawn as before. With 120 text displays added to the 240 item displays, the two views rose from 3,211 to 4,534 fps and from 3,214 to 4,200, and every differing pixel against the old jar was sky or drifting cloud.

Looking up every line in the layout cache each frame took 1.68% of the render thread in a CubeCraft lobby, mostly hashing and comparing cache keys. The box only depends on the font, the display's line layout, background, width, height, shadow, alignment and text color, and a display keeps the same line layout object until its text or line width changes. So the finished box is now stored on that line layout together with every value it was built from and the layout cache's generation, which goes up whenever fonts are reloaded or their options change, and it is only rebuilt when one of them differs. Until every line has been laid out once no box is stored and the display is drawn as before. In a TxBench scene with 600 two-line text displays, text display submission fell from 15.21% to 8.63% of the render thread, and the screenshots were the same.

Culled item displays were still extracted every frame, which resolves their item model, before being dropped at submit. An item display whose item uses a plain vanilla item model, with no properties that select other models over time, now remembers its bounding radius around its position (its model extents through the display transformation, which billboard rotations cannot change) together with the exact render state, item state and model it was measured with. While all three are unchanged and the display is not interpolating, has no visible name, shadow or vehicle, the display is skipped before extraction when a sphere of that radius, at least as large as its hitbox point and view arrow, lies outside the frame's clip volume widened by 16 pixels. That clip volume is built at the start of entity extraction from the same camera projection, view bobbing, hurt tilt and nausea spin the frame draws with, and the frame throws if the projection and camera rotation it then draws with differ. Skipping an item display still updates its interpolation progress, as its extraction would. In the 360-display TxBench scene with hitboxes on, where half the item displays use such models, the two views rose from 2,927 to 3,079 fps (+5.2%) and from 2,957 to 3,048 (+3.1%), with identical screenshots.

### Villager textures

Every villager built the identifiers of its type, profession and profession level textures again every frame, each one a new path string put together and validated character by character, and the render type lookups that followed hashed those new strings again. The identifier only depends on the layer's texture folder, the texture kind and the key, so each layer now keeps the identifiers it built and hands out the same ones. In a TxBench scene with 48 villagers the two views measured +0.0% and +2.0% fps, within noise for a cost of about 0.4% of the render thread in a BedWars lobby.

### Rain culling

Rain and snow are built column by column around the camera every frame. Columns whose vertical span lies outside the camera's view are skipped. Each column draws with its own position-seeded randomness, so the visible rain looks exactly the same.

For every column that is drawn, vanilla also asked the level for the precipitation type at that block, which looks up the biome through the biome zoom noise and the biome temperature. In rain a spark profile showed this at 20% of the render thread. The answer only depends on the chunk being loaded and its biome data, so it is cached per block position and the cache is dropped whenever a chunk is loaded, unloaded or gets new biomes, and when the level changes. The column bounds come from the values vanilla already computed instead of a second heightmap lookup.

### Entity culling

Entities and block entities hidden behind solid blocks are not extracted or drawn. Every 5 ticks the client tick records the culling box and position of every loaded entity, plus every block entity within 64 blocks of the camera whose renderer isn't drawn off screen. A background thread then traces rays from the camera to sample points on the camera-facing faces of each box, through blocks whose state is a solid render cube, and marks it culled when no ray gets through. This runs again every tick the camera moves or a new capture arrives. Ray results per block are cached for the pass, and only the touched cache entries are cleared before the next one.

Entities farther than 128 blocks, glowing entities, all players, entities whose renderer ignores culling and boxes larger than 50 blocks are never culled, and anything found visible stays visible for at least one second. Players are never culled because the capture only runs every 5 ticks: a player stepping out from behind a wall would otherwise stay hidden until the next capture and then appear at once. Culled entities that show their name still draw the name tag and the below-name score through walls, at the same distances vanilla uses. Block entities outside the camera's view are skipped as well, without allocating a box.

Entities that are culled, or were not extracted in any frame since the previous tick, only run a basic tick on the client: vanilla's common tick (old position and rotation, invulnerability timer, position interpolation, tick count), `aiStep`, hurt time and the warden heartbeat. A tick with no frame since the previous one, below 20 FPS, never counts entities as out of camera. Players, the camera entity, vehicles, boats, minecarts, display entities and firework rockets always tick fully.

### Persistent buffer mapping

Every write into a CPU-visible GPU buffer (dynamic transforms, uniforms, fog, clouds, vertex staging) mapped the buffer's memory with `vmaMapMemory` and unmapped it again when the view closed, two native calls per write. A spark profile showed these calls at 2.8% of the render thread. Each buffer is now mapped the first time it is written and stays mapped until it is destroyed. Every mappable buffer is allocated host-visible and host-coherent, so the GPU sees the same bytes at the same addresses without any flush, and vanilla's check that a buffer is not closed while a view is open still works. The global settings and level projection uniforms, written once per frame, keep one view per ring buffer and write through it from the start, so they no longer build a new mapped view each frame. Each draw's transform (two matrices, a color and an offset, 156 bytes in std140 layout) is written straight to the mapped address at the same offsets instead of through the std140 builder; over 200,000 random transforms, including NaN, infinities and signed zeros, both produced the same bytes and end position.

### Texel buffer views

Pushing descriptors that use a texel buffer (the cloud buffer) created a Vulkan buffer view on every push and queued it for destruction two frames later. The view only depends on the buffer, offset, size and format, so it is now kept on the buffer (up to 8 per buffer) and destroyed together with the buffer, after the GPU is done with it. A view that does not fit on its buffer is queued for destruction as before.

Every descriptor push also built its Vulkan structs through LWJGL wrapper objects: one for the write array, one per uniform for the write and one for its buffer or image info, and for texel buffers a long buffer and a create info. The push now writes the same structs straight into the render thread's stack memory with LWJGL's raw field setters, in the same order and with the same values, so the driver receives the same bytes without any of those objects.

### Pipeline switches

Switching pipelines inside a render pass re-applied every uniform ever set in that pass through a hash map pass, and checked the pipeline's color formats against the pass attachments again. Only the new pipeline's own uniforms are now applied, which gives the backend the same values, and the format check runs once per pipeline per render pass.

### Present thread

The frame's queue submit and its present are native driver calls that took a third of the render thread in the prelobby. Both now run in the same order on one dedicated thread, while the render thread already moves on to the next frame. With vsync off, the next frame acquires its screen image just before it copies to the screen instead of at the start, after the present thread has finished, so the render thread builds the whole frame while the previous one is being presented. Every other queue or swapchain call waits for the present thread first, and the same image is presented in the same order. On Windows waking a thread is a system call even when it is not asleep, so each side now marks when it is about to block and the other only wakes it then; the hand-over reuses one job instead of allocating one per frame. With vsync on, the image is still acquired at the start of the frame, so input latency is unchanged. With vsync off the swapchain also gets one more image than vanilla asks for, when the driver allows it. In immediate mode a finished image is shown as soon as it is presented, so the extra image adds no latency; it only means the late acquire does not have to wait for the presentation engine to release an image while the GPU is the bottleneck.

The present thread only wins while the CPU is the bottleneck. With the GPU as the bottleneck, NVIDIA's driver blocks in the late acquire and the GPU loses work, so the frame then runs vanilla's order on the render thread instead: acquire at the start of the frame, then submit and present right after the frame is recorded. Both orders draw the same image. Which one is used is decided from what each order measures about itself over every 128 frames, without ever running the other order on trial: in vanilla's order, a render thread that waits for the GPU less than 10% of the frame time is CPU-bound, so the present thread takes over; with the present thread, an acquire that blocks more than 8% of the frame time means the GPU is the bottleneck, so vanilla's order takes over. In the measured scenes these values are 1.7% against 40% and 1.0% against 19.5%, far from both limits. `/txprofile` reports the share of frames that used the present thread.

Above 4,000 fps the render thread and the present thread no longer go to sleep while they wait. After each submit the render thread waits for the GPU to finish the frame before, and the present thread waits for the next frame to hand over; both used to block in the operating system, and every wake-up from a blocking wait costs scheduler time that sits between the GPU finishing one frame and receiving the next. Now, while the average frame time over the last frames is under 250 µs, the render thread reads the GPU's submit counter in a loop and the present thread checks for its next frame in a loop, each for at most 250 µs before blocking as before. Below 4,000 fps both block right away, so slower scenes run exactly as they did, and the GPU sees the same commands in the same order. Over seven runs of the old build against two runs of the new one, the copy of the Bedwars prelobby went from 10,013 to 10,400 fps on average, faster in every run of all four views (no run of the new build was slower than any run of the old one), while every view of the singleplayer world, at about 1,700 fps, stayed within the old build's range or above it. The cost is CPU time: in the prelobby copy the render thread no longer sleeps while it waits, so it is busy 95 µs instead of 48 µs per frame.

With vsync off, a frame in vanilla's order gets its screen image at the end of the frame before it, right after the render thread stops waiting for the GPU, instead of at its own start after the client tick, packets and input. NVIDIA's driver blocks in `vkAcquireNextImageKHR` for 1 to 2 ms, even with a zero timeout, when the frame before was submitted less than about 0.4 ms after its own acquire returned while the GPU had at most about 0.1 ms of earlier work left: the acquire then only returns about 1 ms after the GPU finished that frame. The GPU runs dry in the meantime, so the next frames are submitted to an idle GPU and block the same way, up to 10 frames in a row at 2 ms each. In GPU-bound scenes client ticks set this off: a tick ran before the acquire at the start of the frame, so only the short recording was left between the acquire and the submit, and the submit came just as the GPU ran out of work. Acquiring right after the wait moves the tick between the acquire and the submit, where it does no harm: in the TxBench translucent station the share of frames that blocked fell from 4 to 5% to about 0.1%. The acquire makes the checks vanilla makes at the start of the frame and only runs once the world has been shown, so loading frames that are held are unchanged. If the surface has to be reconfigured before that frame starts, as after a resize or a fullscreen toggle, the image is handed back by waiting on its acquire semaphore in an empty submit, and the frame reconfigures and acquires as vanilla does. An acquire that fails is reported where vanilla's acquire would have failed, and the image is handed back before the surface is closed on shutdown.

### Submit collections

The hand and screen effect passes drained their submit collections twice per frame and threw away the empty ones, so the next frame built them again with all their phases. Empty collections are now kept and reused; an empty phase draws nothing.

Every model, item, text and shadow submit then looked up the collection for order 0 in the tree map of collections, through `computeIfAbsent` with a lambda: 0.34% of the render thread (2.4 µs per frame) in a CubeCraft lobby with 38 players and 0.56% in a CubeCraft game at 8,417 fps. Since collections are no longer removed, the order 0 collection is now kept in a field and returned straight away; the field is dropped when switching improved transparency clears the map.

### GUI item atlas sweep

At the end of every frame the GUI item atlas walked all its slots looking for slots marked to be dropped after the frame. The sweep now only runs when a slot was marked since the last sweep.

### Animated sprites

Every client tick redraws the animated textures into each mip level of their atlas, one render pass per level, and vanilla draws every sprite on its own: it binds that sprite's frame textures and uniforms and pushes a new descriptor set for each draw. Vanilla's own block textures need 43.9 sprite redraws per tick on average, once per mip level, so 219 draws per tick with 4 mipmap levels, and server resource packs add more. Across 50 captures from servers and singleplayer the atlas tick took a median 5.0% of the slowest 1% of frames, which are the tick frames, and up to 13.0%.

Each atlas now copies every frame of its animated sprites once into one texture per frame size, with the same mip levels, from the same images and regions vanilla uploads. Vanilla kept every frame as its own texture: 594 textures for the block atlas, which now holds the same texels in two textures (16x16 and 32x32 frames) without empty slots. On each tick the sprites vanilla would redraw (interpolated ones every tick, the others when their frame changes) are written into one of three small mapped uniform buffers, and each mip level is one render pass with one instanced draw per frame size. The animation state still ticks in vanilla's code. Every frame ends with one submit and textures tick at most once per frame, so a buffer is only written again after the GPU has finished the frame that read it.

The shader picks the texel vanilla's nearest sampler picks: an atlas pads every sprite by a multiple of 2 to the power of its mip levels, so every pixel samples a frame at the centre of a texel, and pixels in the padding take the nearest edge texel, as the clamping sampler does. It mixes the current and the next frame with the same progress value, computed in the same order as vanilla, and a sprite that does not interpolate mixes its frame with itself at 0, which is that frame. A check build hashed every mip level of all 12 atlases after the upload and after each of the first 300 ticks: 4,816 hashes, none different from the old build, in each of two runs. In the TxBench lobby with ticks running, over three runs of each build in alternating order, the atlas tick took 25.5 instead of 66.6 µs (median), and the 1% low fps rose by 0.3%, 1.6%, 2.7% and 2.6% in the four views while the average fps stayed within -0.2% to +0.6%. Most of what remains is the render pass for each mip level.

### Viewport, scissor and pipeline binds

Every render pass set the viewport and scissor and bound its first pipeline again, even when the command buffer already had exactly that state from the previous pass. The bound pipeline and both dynamic states stay valid across render passes in the same command buffer, so a viewport, scissor or pipeline that is already set is no longer recorded again. `vkCmdBindPipeline` alone was 2.8% of the render thread in the BedWars prelobby. Pushed descriptors also stay valid across render passes, so the check that skips pushing an identical descriptor set with the same pipeline layout now spans the whole command buffer instead of a single pass. The remembered state is dropped whenever a new command buffer starts recording. The scissor is compared before its Vulkan struct is built, and a changed one is written straight into stack memory, so a GUI draw that keeps the scissor builds nothing.

### Particle vertices

Particles were turned into vertices one at a time: a callback and a new rotation per particle, a new vector for every corner, and a separate vertex reservation for each vertex. Each particle layer is now written in one pass straight from the stored particle arrays into one reservation, with the same corner math, colors, UVs and light, so the vertex data is identical. Each vertex position is computed in local floats, the same multiply then add JOML's `mul` and `add` do (Java never fuses them), instead of going through a shared vector object's fields (3.4 to 3.8% of the render thread with 750 particles at a CubeCraft spawn, inside particle preparation). A layer is written this way only when the buffer can reserve it exactly as described under direct vertex writes; buffers that cannot, including one that would have to grow for the layer, still go through the vanilla per-particle path.

### Model part rotation

Every rotated model part (entity limbs, heads, armor) built a new quaternion from its three angles and rotated both its pose matrix and its normal matrix by it, and each of the two rotations worked out the same nine rotation terms from the quaternion again. The quaternion is now computed in local values with JOML's own formula, its rotation terms are worked out once, and both matrices are rotated by them with JOML's own formulas, including its separate paths for identity, translation-only, affine and general matrices and the matrix property flags it sets. Most rotated parts turn around only one or two axes, so a half angle of exactly zero now skips its sine and cosine: JOML returns that same zero and exactly 1 for it, so the matrices are identical. JOML's fast math mode still computes them. A test of 3,000,000 random poses and angles, including signed zeros, infinities and NaN, against vanilla's rotation with JOML 1.10.9 matched every value and property flag.

On the render thread the nine rotation terms are also kept in a table of 1,024 entries keyed by the bit patterns of the three angles. Armor layers copy the angles of the body they are worn on, so a player in armor rotates its head, body, arms and legs by the same angles up to three times per frame, and the later rotations reuse the terms of the first. An entry is only used when all three angles have the same bits, and it holds what the same formula produced, so the matrices are identical; other threads, which bake block entity models into terrain sections, compute the terms as before. A test build that recomputed the terms for every cached rotation matched all of them in 30 million rotations. In a crowd of 40 armored mannequins and 41 armor stands, the rotation share of the render thread fell from 4.65 to 3.15%.

### Item model bounds

Items on shelves and dropped items asked for their model's bounding box every frame, and because their render state is cleared or recreated every frame, vanilla rebuilt the box from every vertex of the model each time (about 1% of the render thread at a server spawn full of shelves). The box only depends on the model's extents, its item transform, the hand and its local transform, so single-layer items now keep it in a cache keyed by exactly those values. Items with Fabric mesh quads, which add their own vertices to the box, and multi-layer items still compute it every time. Each item render state also keeps the cache entry it used last and compares the four values with it directly before looking anything up, so a held or displayed item whose render state is reused from frame to frame no longer hashes its 16 transform values and walks the cache's table every frame (0.86% of the render thread in a CubeCraft lobby with 416 entities).

### Raycast air

Every block a raycast passes through (the per-frame crosshair pick, the third-person camera collision) asked the block for its shape. Air never has a shape in any raycast mode, so air blocks now return the empty shape directly.

### Particle collision

Every particle with physics checked its movement against the blocks around it each tick by collecting every block collision shape in the swept box into a new list (up to 0.8% of the render thread at a server spawn full of dust particles). Particles have no entity colliders and no world border, so when no block in that box yields a collision shape, vanilla returns the movement unchanged. The box is now first checked directly in the chunk sections with vanilla's own rules: all-air sections are skipped whole, the corner cells around the box are skipped as vanilla's cursor skips them, a cell on a face of the box only counts when its block has a large collision shape and a cell on an edge only for a moving piston, and every other non-air block is asked for its collision shape. A full block counts when it intersects the box and any other shape when its bounds overlap the box, which every shape vanilla would keep does. Only a box where some block may collide goes through vanilla's collision. Checking only for all-air boxes sent every particle beside a block through vanilla's collision: in a CubeCraft lobby, ticking particles took 32% of the slowest 1% of frames, 21% of them in vanilla's collision. Debug worlds, whose blocks do not come from the chunk sections, always use vanilla's collision. In a benchmark scene with 8,500 dust, block, item and poof particles around walls, fences, stairs, slabs, lanterns and glass panes, a build that ran both checks on all 6,320,000 particle moves found no move where the scan skipped a collision vanilla would have made, and 83% of the moves skipped vanilla's collision. Particle collision went from 6.68% to 5.49% of the render thread there, with vanilla's collision from 5.08% to 2.50%.

Most particles still read all 19 cells around their box, but a cell beside the box only matters for a block whose collision shape reaches out of its cell, such as a fence or a wall, and a cell on an edge only for a moving piston. Each chunk section now remembers whether its block palette holds any such state, using vanilla's own palette check, and in a section whose palette holds none only the cells inside the box are read. The answer is kept together with the palette it was worked out from, that palette's size and how often the section was read from a chunk packet, which can refill the same palette, so it is worked out again whenever the palette is replaced, grows or is read again. A test build that ran the full scan next to the shortened one found no difference in 8.4 million particle moves, 2.4 million in a world with 412 entities and about 13,500 particles and 6 million in the benchmark scene with walls, fences, stairs and slabs. In that world, under ZGC, the scan went from 2.54% and 2.44% to 0.50% and 0.65% of the render thread over two runs per build, particle ticking from 4.41% and 4.43% to 2.59% and 3.03%, the 1% low from 215 and 214 to 254 and 255 fps, and the average from 894 and 896 to 901 and 914 fps.
### Particle removal

Each particle group keeps up to 16,384 particles in an `ArrayDeque`, ticks them through its iterator and removes every dead particle with the iterator's `remove`, which shifts every particle on the shorter side of it by one slot. When particles with long and short lifetimes are mixed, such as campfire smoke and fireflies next to dripping water and falling leaves, they die in the middle of the queue: in a world with 412 entities and about 13,500 particles, `/txprofile` put these removals at 5.6% of the slowest 1% of frames, which are the tick frames. Each group now takes every particle off the front once per tick, ticks it and puts it back at the end while it is alive, so the same particles are ticked in the same order, the survivors keep their order, and a dead particle's limit count is lowered at the same point as before. New particles only join a group after every group has ticked, in vanilla as here. In that world, under ZGC, particle ticking went from 4.95% and 5.07% to 4.41% and 4.43% of the render thread over two runs per build, and the 1% low from 200 and 190 to 215 and 214 fps.

### Particle frustum test

Every frame, each quad particle group walked all of its particles to test each one's position against the view frustum before drawing it. The particles lie scattered in memory, so in a world with about 13,500 particles most of these tests started with a cache miss, and drawing particles took 5.8 to 6.3% of the render thread even with the camera facing away from most of them. A particle's position only changes while it ticks, and particles only join or leave a group while particles tick, so each group now counts these changes, and after a change it copies every particle's position into one array of doubles before its next frame. Each frame tests that array with the same frustum call and the same values, and only reads a particle whose position passes, still in the group's order, so the same particles are drawn in the same order. A test build that compared the copied position with each particle's own position for every particle in every frame found no difference in 210 million particle frames in that world and 904 million in the benchmark particle scene. The array holds three doubles per particle, at most 393 KB for a full group of 16,384 particles. In that world, under ZGC, drawing particles went from 6.25% and 5.81% to 3.88% and 4.02% of the render thread over two runs per build, and the frame rate from 947 and 920 to 963 and 969 fps.

### Particle extraction

Each particle in view then read its own fields every frame to build its quad: previous and current position, roll, size, texture coordinates, color, light, layer and camera facing mode, spread over the particle object and its sprite. All of these only change while particles tick or join a group, so together with the positions above each group now copies them into arrays once per change or client tick, and each frame builds the quad from the arrays with the same arithmetic, in the same order. Particle types that draw themselves differently (fireworks, shrieks, vibrations, dust color transitions and particles that fly towards a position) are still drawn by their own code, and types that work out their size or light for the frame (flames, portals, lava and others) still ask the particle for those two values every frame. A test build that compared every stored value with the particle's own fields in every frame found no difference in the scene with every particle type at once or in the benchmark scenes. In that scene, which also holds every block and entity type, fps rose from 375 and 378 to 406 and 404, and the render thread spent about 190 µs less per frame.

### Ambient block ticks

Every client tick, 1334 random blocks around the player get their ambient effects (campfire smoke, dripping water, ambient particles), and each one was looked up twice, once for the block and once for its fluid. The fluid is part of the block state, so it is now read from the block state already looked up. The debug world, where block lookups do not come from the chunk sections, keeps the second lookup.

Every one of those blocks that is not a full block, which includes every air block, then reads the ambient particles environment attribute at its position. A positional attribute read walks the attribute's layers with a for-each loop over an immutable list, whose iterator class is shared by every immutable list in the game, so the JIT calls it through an interface dispatch. In a BedWars profile that iterator took 1.46% of the slowest 1% of frames, which are the frames that run a client tick. The layers are now walked by index, in the same order and with the same calls.

### Idle block entity ticks

Every client tick, each block entity with a client ticker goes through vanilla's ticking wrapper, which looks up the block state at its position in the chunk and checks it against the block entity's type before calling the ticker. Those lookups land on block entities spread over the whole render distance, so nearly every one misses the CPU cache: in a singleplayer profile at render distance 32, block entity ticking was 20% of the slowest 1% of frames, which are the frames that run a client tick, and the chunk lookup inside the wrapper was half of that. Around the spawn of that world, 427 of the 575 block entities with a client ticker are chests and spawners. A chest, trapped chest or ender chest whose lid is resting (closed and not opening, or fully open and not closing, with last tick's openness equal to the current one) and a spawner with no player in range whose last spin equals its current spin change nothing when they tick: the chest only copies its openness into last tick's openness, the spawner its spin into last tick's spin. These block entities now skip the tick before the wrapper's lookup. Only these exact vanilla classes in a client world are skipped, and a chest starts ticking again on the tick its lid starts to move, a spawner on the tick a player comes in range, so the game state is the same after every tick. The one difference is the wrapper's warning for a block entity whose block state does not match its type, which an idle chest or spawner no longer checks. In the singleplayer benchmark with ticking on, block entity ticking went from 0.47% and 0.42% to 0.13% and 0.24% of the render thread, the wrapper's chunk lookup from 0.14% and 0.21% to 0.03% and 0.05%, and the whole client tick from 1.33% and 1.35% to 1.11% and 1.00%.

### Translucent sort reuse

Translucent entity, item, text and particle quads are sorted back to front before every upload. Vanilla works out a distance for every quad and sorts the quad indices with fastutil's merge sort, which calls a comparator lambda for every comparison and keeps equal distances in index order; that comparator call site is shared by every merge sort in the game, so it is not inlined, and without Sodium the sort took 3.1% of the render thread in the busiest benchmark scene and 3.8% in the particle scene. Each sort's result is now remembered by its position among the frame's sorts, and the next frame first checks in one pass whether the remembered order is still sorted under the new distances (ties ordered by quad index). If it is, it is exactly the order the stable sort would produce, so it is used without sorting. Otherwise every distance becomes an integer key that orders exactly like `Float.compare` (negative zero below zero, every NaN equal and above infinity), each key is packed with its quad index into one long, and up to 80 quads are sorted with an in-place quicksort that switches to heapsort if it recurses too deep and finishes small ranges with insertion sort, and larger counts with a radix sort that skips passes where every key lands in the same bucket. The index breaks every tie, so both give vanilla's order. None of this allocates in steady state: the quad centers are decoded into an array kept per quad count and zeroed before each use, the sort keys go into one reused array, and each remembered order is rewritten in place. The index writer reads the remembered order directly, and only callers outside the upload path get their own copy. Translucent terrain, which is sorted on the section build threads, packs the same keys straight into one array and sorts it with the same in-place quicksort, and fewer than 16 quads are ordered by a stable insertion sort on the keys, so those sorts never allocate more than vanilla's did. A test of 141,548 sorts against vanilla's own sorters over 3,000 simulated frames, with repeated and moved quads, ties, signed zeros, infinities, NaN with different payloads and up to 4,000 quads, matched vanilla's order every time through both the remembered and the fresh path. Uploads sorted by distance to the camera, which is every world draw with a perspective projection, now skip the quad center array altogether: the keys are worked out straight from the vertex data in one pass, with vanilla's center formula and JOML's own `distanceSquared` called on the same zero origin, and the sorted indices go straight into the mapped index buffer without a sort state object or a distance lambda per quad. An offline test of 300,000 such sorts (93 million quads with random bit patterns, NaN, infinities, signed zeros, repeated quads and up to 2,000 quads per draw, split into random slices) matched vanilla's center, distance and stable merge sort order every time. In an offline loop of 30 player-skin draws of 36 quads and two larger draws per frame, sorting took 3.8 µs per frame instead of 5.4 to 8.2. In the combined benchmark scene (hub, armored crowd, particles, item displays and overview) the frame rate was 1.4 to 5.9% higher in every station over three runs per build, and lower in only one of the fifteen paired runs.

### Transient command buffer

Every frame started a command buffer for copies into transient GPU memory and submitted it first, even though nothing in the game records such copies in a normal frame. That buffer is now only started when the first copy is recorded, and it is then placed first in the frame's submission, exactly where it would have been. Frames without such copies submit one command buffer fewer.

### Continued render passes

Ending a render pass recorded the end of the rendering instance and a full barrier right away, and the next pass began a new instance, even when it drew into exactly the same color and depth textures. The end of a pass is now held back. If the next pass uses the same attachments and render area, clears nothing and nothing else was recorded in between, it keeps drawing in the same rendering instance, as happens from the sky pass into the main world pass in clear weather. Draws inside one rendering instance keep their order for color, depth and blending, and a pass cannot sample its own attachments, so the image is the same. Anything else that records a command, ends the command buffer, or begins a different pass ends the held pass first, exactly as before. The GPU pass profiler disables this while it records.

### Long selection lists

Filling a scrolling list (server list, world list, resource packs) placed each new row by summing the heights of every row already in the list, so filling n rows took n² steps: about 7.3 million for a 3,817-entry server list, an 88 ms freeze when the multiplayer screen opened. While a list is being refilled, each row's position is now carried over from the previous row by adding that row's height, the same value vanilla's sum gives.

### Server icons

Every server list ping decoded the server's icon after removing newlines from its base64 text with `String.replaceAll("\n", "")`, which compiles and runs a regular expression over text that is often tens of thousands of characters long. Pinging the 4,109 servers of a large list spent 12.5% of all CPU time there. The newlines are now removed with a plain character replacement, and text without a newline is used as it is, which gives the same string.

### Frustum box test

Every entity, block entity and rain column visibility check asked JOML for a full box/frustum classification (outside, inside or intersecting), which tests each plane twice, and then only used whether the box was outside. The check now uses JOML's plain box test, which runs exactly the first of those two tests per plane in the same order, so the answer is identical with half the plane math.

### Dynamic transform equality

Each draw's model-view, color, offset and texture matrix are compared with the previously written ones to reuse the uniform slice. That record's generated `equals` went through method-handle dispatch on every comparison (0.2 to 0.4% of the render thread). It is now a plain comparison of the same four components with `Objects.equals`, the cheap vectors first, which returns the same answer.

### Identity model parts

Every visible model part pushed a copy of the pose stack, applied its offset, rotation and scale, drew, and popped the copy again. For parts with no offset, no rotation and unit scale (roots, hats, jackets, sleeves and other overlay layers) that only copied two matrices and translated the copy by zero. Such parts now draw and recurse into their children on the current pose directly; parts with any transform still push, transform and pop. Translating a finite matrix by zero leaves every value as it was, apart from turning a negative zero translation into a positive zero, which does not change any pixel.

### Model part poses

A rotated model part pushed a copy of the parent pose, both matrices and the normal flag, then translated the copy, which rewrote its last column from the values just copied, and then rotated it, which rewrote the upper three rows and the whole normal matrix again; each step also looked the top pose up again. The new pose is now written once: the translated last column is worked out from the parent with JOML's own translation formulas and property rules, and the rotation reads the parent's upper rows and normal matrix and writes its results straight into the next pose slot of the stack, which is added the same way vanilla adds one when the stack has none yet. Parts with an offset but no rotation still copy and translate the way vanilla does. A test of 8,000,000 random parent poses (identity, translation-only, affine, perspective and arbitrary matrices, with stale deeper slots and with stack growth) and part transforms, including signed zeros, infinities and NaN, matched the separate copy, translation and rotation in every value (counting any NaN as the same NaN), property flag and normal flag, and both matched vanilla's quaternion rotation; the in-place rotation that `translateAndRotate` still uses for arms and other callers went through the same test and through 1,000,000 rotations of identity poses. In an offline benchmark pushing a part took 33.0 ns instead of 37.4 ns, most of which is the rotation's sine and cosine, and over three profiles per side pushing transformed parts went from 39.2 to 34.0 µs per frame in the entity station and from 18.7 to 14.0 µs in the busiest one.

### Model pose reset

Every model reset its parts before animating by walking an immutable list through its iterator. The parts are now copied into an array when the model is built and reset in a plain loop, with the same parts in the same order.

### Bare armor stands

Before drawing its layers, every armor stand set up its full pose and then asked the armor, held item, wings and head layers to draw, even when it wore and held nothing, which is what servers use for floating text. When the renderer has exactly the vanilla layers and the stand has no equipment, no held items and no head, that pose setup and the four empty layer calls are skipped. The stand's own model still animates when it is drawn.

### Cuboid normals

Every entity model cube transformed, normalized and packed the normal of each of its faces every time it was drawn, and every item quad did the same for its face. The render thread now keeps the packed normal of each of the six face directions for the current normal matrix, and drops them as soon as any of the matrix's nine values or its trusted-normals flag differs bit for bit, so every cube face and item quad gets exactly the bytes vanilla's transform would produce. Opposite faces use exactly the negated direction, and vanilla's normal packing is symmetric around zero, so a direction whose opposite is already known takes its bytes negated instead of being transformed again, which gives the same bytes (checked on 9 million random direction pairs and matrices including NaN, infinities and signed zeros). Faces whose normal is not one of the six direction vectors are transformed as before, and so is anything that goes through vanilla's per-vertex path.

When the normal matrix is new, a cube fills all six directions at once: the down, north and west normals are transformed and their opposites negated. The transform, the normalization of untrusted normals and the packing are written out in local floats with JOML's and vanilla's own formulas instead of going through a new vector per normal. Vanilla clamps each component with `Mth.clamp` before scaling it to a byte; the same byte now comes from two comparisons, checked against vanilla's packing for all 4,294,967,296 float values. The nine matrix values are compared by folding their bit differences into one value and testing it once. Comparing them one by one gave the JIT compiler nine separate branches, and whenever a new entity rotation first differed at a matrix value that had always matched before, the compiler threw away the compiled entity cube writer and rebuilt it: three times within 32 seconds in the SuperTest world, against none with the single test. The frame rate there stayed the same over three runs per build, since the writer was rebuilt within 45 ms each time; the change keeps the writer from dropping back to unoptimized code while new rotations appear.

### Collision cursor

Block collision scans (particles moving near blocks, the player's suffocation check) walked their cells by splitting a running index with two divisions and two remainders per cell. The cursor now steps x, then y, then z with counters, which visits the same cells in the same order (checked against the division form on every box up to 12 by 12 by 12).

### Render type equality

Batching draws compares prepared render types with their generated record equality, which went through method-handle dispatch and compared the name string before anything else. It now compares the same six components with `Objects.equals`, cheapest first (pipeline, transform slice, scissor, OIT set, name, textures), which returns the same answer. Their hash code is computed by hand with the record's own formula, each component's hash added to 31 times the hash so far, with the transform slice and the OIT set (both records) expanded the same way and the texture list keeping its own hash code (see texture lists below). The generated record hash runs through a chain of method handles that the JIT inlines in some runs and not in others: with the same build, grouping the draws of 200 item displays spent 7.3% of the render thread in it in one run and 0.1% in the next. A prepared render type is made new for every lookup, so the hash is not kept. The transform slice inside it, a buffer slice record, compared and hashed itself the same generated way, and grouping draws compares slices on every lookup (0.88% of the render thread in one run, 0.15% in another); its `equals` and `hashCode` are now written out with the record's own rules, the buffer compared with `Objects.equals` and the offset and length with `==`, and a test build matched the JDK-generated methods in 54.5 million calls. A test build that compared every hash with the one the JDK generates for the record found no difference in 5.4 million hashes, and over three runs per build in a scene with entities, item displays, particles and a HUD the average frame rate and 1% low went up in all five views.

### Pipeline vertex formats

Every time a feature group adds a draw, its render type asks the pipeline for its vertex format, and the GUI renderer does the same for every new GUI draw. The pipeline read it from its list of formats through fastutil's unmodifiable list wrapper, and in a BedWars profile `RenderType.format` took 0.51% of the render thread. Each pipeline now also keeps its formats in a plain array, made from that list when the pipeline is created, and answers from the array. The list never changes, so every caller gets the same format.

### Vertex upload copy

Every frame's entity, text, item, GUI and debug geometry used to be written into a CPU-side staging buffer, then copied by the GPU into the real vertex and index buffers, with a barrier around each copy. That was 5 copies per frame and 0.018 ms of GPU time in a GPU-bound world. The vertex and index buffers are now allocated mappable, and the vertices and sorted indices are written straight into them, so both copies and the staging buffer are gone. Buffers only return to the pool after the GPU has finished with them, so nothing in use is overwritten. Each slice is copied straight from the vertex builder's memory with the same validity and overflow checks, and the GPU receives identical bytes.

That copy still took 4.9% of the render thread across the benchmark scenes and 11.7% in the entity scene. The mappable buffers sit in GPU memory the CPU writes over PCIe, so the time is the bytes crossing the bus, and the builders cannot write there directly: draws are revisited while they are built (particle layers alternate for every particle submit, and a reorderable group goes back to its earlier draw whenever a render type comes back), so the builder memory holds a draw in pieces that vanilla's layout puts back together, and the final offsets are only known once every group is built. The world's entity, text, item and particle vertices are now copied on a dedicated thread while the render thread prepares terrain, which is the next thing the frame does. Before handing out the first draw that reads the buffer, and before ending the frame's draws, the render thread copies every 32 KB piece the copy thread has not started yet itself and then waits for the piece in progress, so at worst it waits for one piece that is already being copied. Hand, GUI, item atlas and picture-in-picture geometry is drawn right after its upload, so it is copied on the render thread at its first draw. The same slices go to the same offsets, sorted indices are still written on the render thread before the copy starts, and the builder memory is only released after the copy has finished. A test of 7,000 simulated uploads with up to 400 draws, 3,000 draw switches and slices of up to 2.6 MB, finishing before the copy thread started, while it was copying and after it was done, matched vanilla's buffer byte for byte every time, including the padding between draws, and nothing was written after the copy had finished. When the level is drawn a second time before the frame is submitted, as some mods do, the second pass copies its own vertices directly as every later pass of the frame does, and the copy already running in the background is left to finish as before instead of being started again, which crashed the game.

Waking the copy thread from sleep for every frame took 1.02% of the render thread in a BedWars game at 6,682 fps. Above 4,000 fps the present thread is already spinning while it waits for its next frame, so it now takes the copy while it spins, and the copy thread is only woken when the present thread is not spinning. Either thread claims the same 32 KB pieces and the render thread finishes and waits for them as before, so the same bytes reach the same offsets whichever thread copies them. In a benchmark hub of lobby blocks with six named armor stands, five named villagers and five text displays, the render thread waited for the copy in 0.11 to 0.61% of its samples instead of 1.05 to 1.89%. Together with the pipeline vertex format and environment attribute layer changes below, the hub went from 10,394 to 10,649 fps over three runs per build, faster in every run of all four views.

The present thread is often still presenting the frame before when the copy is queued, so the copy thread was still woken in most frames: in the CubeCraft prelobby at 10,224 fps that wake-up took 3.39% of the render thread, while the copy itself took 2.2% of the copy thread's core and 0.47% of the render thread. Above 4,000 fps the copy thread is now never woken. The present thread takes the copy as soon as it is back in its wait loop, and the render thread copies whatever is left before its first draw, as it already did. In the benchmark hub, where the present thread was already taking most copies, the frame rate stayed within run-to-run noise (9,876 against 10,075 fps over three runs per build).

In scenes full of entities the copy thread still had not finished when the render thread reached the first draw that reads the buffer, so the render thread copied the rest itself. Recording a draw never reads the vertex buffer; only the GPU does, after the frame's commands are submitted. The render thread now finishes a copy that runs in the background only when the frame is submitted, or earlier when the vertex builder is closed, and releases the builder's memory and the mapped view at that point. The outline scissor only needs the outline bounds, which are the first jobs in the queue, so it waits for those jobs alone. Copies that do not run in the background, such as the hand and GUI geometry, still finish at their first draw. The copy only runs in the background on the Vulkan renderer, where a submit exists to finish it; on OpenGL every copy finishes at its first draw, because nothing finished the background copy there, so the buffer stayed mapped while it was drawn and crashed the game when its spare was closed. Over three profiles per build in a benchmark crowd of 179 armor stands and villagers with hitboxes shown, the render thread's share of the copy went from 10.8 to 20.5% to 8.4 to 11.5%, and the frame rate from 1,961 to 2,143 fps on average. A check build compared every copied byte in the GPU buffer with its source as each copy finished, in a scene with glowing entities and hitboxes, without a mismatch. With clouds turned off, the benchmark's static stations rendered the same pixels with and without this change; with clouds on, a few cloud edges differ, because clouds sit at the game time plus the frame's partial tick and a faster frame catches them at a slightly different position.

The first-person hand pass right after the world writes into the same shared builder, and that used to finish the world's copy before the hand's first vertex. In a CubeCraft lobby with 38 players at 1,387 fps the render thread spent 35 µs of every frame there, 33.9 µs of it copying, while the copy thread used 11.4% of a core, so the copy was still running when the hand pass began. A second copy thread did not shorten it: 2 MB took 110.6 µs from hand-over to the last byte with one thread, 7.5 µs of it waking the thread, and 107.0 µs with two, because the time is the bytes crossing PCIe. The hand and screen effect passes now append their vertices after the world's in the builder memory, which stays allocated until the world's copy is released, and their uploads copy their few KB into their own buffer straight away, so the world's copy keeps running until the frame is submitted. If the builder memory has to grow while the copy reads it, the resize first waits for the copy to complete, since growing can move the memory; nothing is released at that point. The check that finishes copies on reuse also moved from every vertex builder request to the request that starts a new builder: in the first version, which checked on every request, the crowd station of the benchmark lost 5.0% over seven runs per build. The benchmark player is a spectator and has no hand pass, so a hand suite stands on an invisible barrier in creative with a sword at the entity, hologram and everything stations. There every hand upload went beside a running world copy, the world's copy was done when the frame was submitted, and a check build that grew the builder memory at every hand upload waited at every one of them without a fault. The benchmark copies finish long before the hand pass, so the frame rate stayed within noise over seven interleaved runs per build (+0.7%, -0.2% and +0.6% at the three stations), and the screenshots of both builds showed the same three cloud positions and otherwise identical pixels.

### Uniform writes

Every entity, text or item draw with its own transform wrote that transform into a ring buffer through a fresh mapped view of the buffer. Each write allocated a pointer buffer, a byte buffer, a buffer slice, a mapped view and its close callback (over 16 MB/s of garbage in a busy server lobby). Under Vulkan each ring buffer now keeps one mapped view, opened the first time it is written and closed with the ring buffer, and every transform is written through it. Each transform is written at the same offset with the same limit, so the GPU reads identical bytes. The memory is host-coherent, as it was before, so no flush is involved. Other backends keep mapping per write.

The global settings uniform (camera position, game time, screen size, RGSS) and the level projection matrix were written every frame with a GPU copy from a staging buffer followed by a full barrier that waits for all earlier GPU work, two per frame. Both are now written straight into the next buffer of a ring of mappable buffers, the same kind vanilla uses for fog and clouds, which waits for the GPU only when it comes back to a buffer the GPU may still read. The bytes are the same, so is the moment the GPU sees them: draws recorded before the write read the old buffer, draws after it the new one.

When a uniform write equals the previous one, the previous block is reused. That reuse now also returns the slice object made for that block instead of a new one, as long as it still points at the same block of the same buffer, which is what a new slice would describe (3.8 MB/s in the BedWars prelobby).

### Model cube writes

Every model part drew its children by iterating its child map, which created an iterator object per model part per frame (5.2 MB/s in a world with many slimes). Child maps are fastutil array maps, so the children are now read in the same order straight from the map's value array. Any other kind of map keeps the iterator. A part's cubes are walked by index in the same order instead of through the cube list's iterator.

### Model cube corners

A model cube has 8 corners, but vanilla transformed each of its 24 vertices separately, with 9 multiplications and 9 additions each (`ModelPart$Cube.compile` was 18 to 22% of the render thread in the benchmark's entity scene). Every cube with all six faces is built by vanilla's cube constructor from 8 corner vertices in a fixed order per face, which a mirrored cube reverses, so its two x, y and z values are read from three of its vertices. JOML evaluates a position as `m00 * x + (m10 * y + (m20 * z + m30))`: the innermost sum depends only on z and the middle one only on y and z, so they are worked out for the 2 z values and the 4 y and z pairs and shared between the corners. That is 42 multiply-adds per cube instead of 216, each with the same operands in the same order. Matrices JOML treats as identity or pure translation keep its shortcuts (the position itself, or the position plus the translation). The vertices are then written in vanilla's order with their own UVs and the face normals from the normal cache; the overlay and light go out as one 8-byte store and the normal as a 2-byte and a 1-byte store, the same bytes as vanilla's separate stores, and the padding byte after the normal stays untouched as in vanilla. Cubes drawn through a sprite UV mapping (signs, chests, banners, beds, shields and other atlas-textured models) take this path too, with every UV passed through the same mapping calls in the same order, and so do cubes drawn into a position, UV and color buffer such as the glowing outline, where vanilla drops the overlay, light and normal. Cubes with hidden faces keep the per-vertex direct write, and every buffer that cannot reserve the cube keeps vanilla's path.

To write a cube, the writer still read three of its corner vertices and the texture coordinates of all 24 vertices from the cube's faces: six face records, six vertex arrays and 24 vertex records, scattered in memory, for every cube of every entity in every frame. They never change after the model is built, so each cube now copies them into one array of 55 floats the first time it is drawn, and writes from that array with the same values. The copy is made again if any of the cube's six faces is replaced. In the scene with every entity type at once, fps rose from an average of 404 to 426 over four runs per build in both orders, and below the sky the benchmark scenes matched the previous build pixel for pixel.

A comparison against vanilla's cube drawing over 400,000 random cubes (mirrored or not, grown, flat, NaN, infinite and huge coordinates and texture sizes), each written as plain and sprite-mapped entity vertices and in both textured formats under random matrices, matched every byte of 38 million vertices. NaN positions compare as NaN: vanilla itself writes different NaN bit patterns for the same input once the JIT has compiled it, and an interpreted run matched every bit. In an offline benchmark on the real classes a cube took 56 ns to write instead of 69 ns before (87 ns in vanilla).

### Entity culling boxes

Every entity checked against the view frustum got a new bounding box, grown by half a block, every frame (about 11 MB/s in singleplayer). The check now works out the six coordinates of the grown box from the culling box with the same arithmetic vanilla's box constructor uses, runs vanilla's invalid and zero size tests on them and passes them straight to the frustum test, so neither a still nor a moving entity creates a grown box, and no box is kept per entity. A box is only created where vanilla needs one beyond that test: the four block box around an entity whose culling box is invalid, and the box spanning a leashed entity and its holder when neither is visible on its own.

### Particle draw maps

Every particle group built two new identity maps per frame to collect its draws and textures per layer. The maps are now cleared, when they hold anything, and reused once the frame's particles are drawn. A cleared map keeps its table size, so it lists its layers in the same order a new one would; a map that ever held enough layers to grow is dropped instead of reused.

### GUI layer search

Every GUI element is placed one layer above the highest element it overlaps. To find that layer, vanilla walks the layers of the current stratum from the top down and asks every element on each layer for its bounds through an interface call, until one overlaps. Elements drawn after the HUD, such as an overlay's minimap or effect list, are checked against every element already placed there, so the work grows with the square of their number: in a CubeCraft lobby with a minimap of 9 players this search was 5.85% of the render thread. Each layer now keeps the left, top, right and bottom edges of its elements in one flat array of numbers and checks those, with the same overlap test, in the same top-down order, so every element lands on the same layer. The array is filled from the layer's lists right before they are searched, so elements added any other way are counted too, and it is rebuilt from scratch if a list was replaced or got shorter. A test build that also ran vanilla's search on every layer it visited found no difference in 35 million layer checks. With 26 effects on the player the frame rate went from 8,190 to 10,890 fps and the 1% low from 3,470 to 4,200 fps over three runs per build, with identical screenshots.

### GUI glyph runs

Every glyph of GUI text became its own GUI element: a new glyph state object added to a list, then on its own way into the mesh it built a texture setup with two sampler lookups, compared its pipeline, texture and scissor with the previous element, and converted the text's 2D pose into a 4x4 matrix. All glyphs of one text share its pose and scissor, and consecutive glyphs from the same font texture share the pipeline and texture, so they never start a new draw. Such a run of glyphs is now one GUI element that converts the pose once and writes each glyph's vertices in the same order with the same matrix, into the same draws as before. With F3 open in TxBench the lobby station rose from 10,906 to 11,288 fps (+3.5%), and the static F3 lines matched the old jar pixel for pixel.

### Buffer slices

Asking a GPU buffer for a slice covering all of it created a new slice object each time, and vanilla does that for every entity, item, text, GUI and particle draw each frame. The slice is now created once per buffer, since a buffer never changes size.

### Feature phase loop

Each frame, the translucent pass walked every feature phase of every submit collection, and each phase with nothing to draw built an iterator over an empty list (about 8 MB/s in a BedWars game). Phases with no groups now return straight away, and the rest are walked by index in the same order.

### Projection uploads

The GUI, the item atlas and picture-in-picture renderers upload their projection matrix to the GPU with a buffer copy every frame, because their projection's version number changes each time it is set up, even when the matrix stays the same. Each projection buffer now remembers the matrix it last uploaded and skips the copy when the new matrix is bit-for-bit the same, so the buffer already holds exactly those bytes.

### Suspicious sand and gravel

Every suspicious sand and gravel block in view built a full render state each frame, including an item render state with its own matrices (about 45 MB/s of garbage on a BedWars map), although it only draws its buried item while it is being brushed. Blocks that have not been brushed at all now skip the render state, since vanilla's renderer draws nothing for them.

### Block entity distance

Every block entity in view allocated a vector for its center to check whether it is within the renderer's view distance (about 6 MB/s on a BedWars map). Renderers that use the default distance check now compute the same differences and squares directly from the block position, in the same order, so the result is identical. Renderers with their own check, such as beacons, still run it.

### Block entity light

Every block entity in view looked up its light every frame: the block state at its position, then its block and sky light, 0.87 to 1.19% of the render thread in CubeCraft lobbies. Each block entity now keeps the light it last got with the block state and a light generation. Readers only ever see a storage's visible section map, which is replaced in exactly one place, and sections are copied before they are written, so the client's light values can only change when a client storage publishes a new map; that bumps the generation. The block entity's state follows the block at its position (the chunk updates it or replaces the block entity), so the cached value is returned while both match. Another light engine than vanilla's turns the cache off. A check build that looked up the light again on every cache hit, through stations that placed glowstone beside banners, chests and signs and removed it again, found 0 mismatches in 318,809 hits. In a field of 400 standing banners, measured with the same build and the cache switched on or off over four interleaved runs each, extracting the block entities took 25.2 instead of 41.4 µs per frame and the frame rate rose from 4,242 to 4,563 fps (+7.6%) and from 4,427 to 4,774 fps (+7.9%) at two camera positions, about 40 ns per lookup. A run without the cache rendered the same pixels as every run with it; the other runs differ only in where the banners' cloth is in its sway.

### Render type textures

Every time an entity, item or text render type was prepared for a frame, it built a new list of its textures (overlay, lightmap and each bound texture with its sampler), allocating the list and one record per texture. Each render type now keeps the list it built last and returns it again when every entry would be the same: same name, same texture view object and same sampler object, looked up the same way and in the same order as before. Any change, such as a reloaded texture or a different lightmap, builds a new list. Checking whether the list is still current walked the render type's texture map, a hash table of 16 slots for one or two textures (0.84% of the render thread at a CubeCraft spawn). A render setup's texture map is complete once the setup is built, since vanilla only adds textures through its builder before building, so the names and bindings are read into two arrays once, in the map's own order, and the check walks those. The texture manager counts every change to its texture map (registering, releasing or closing textures), and each render setup keeps the textures it looked up until that count changes, so the check no longer looks every texture up by name on each draw; each texture's current view and sampler are still read every time. The list keeps its hash code, the same value a list of those textures always has, so hashing a prepared render type no longer walks the textures (1.24% of the render thread in slow frames). Drawing a render type binds its textures with an indexed loop instead of a new iterator per draw (2.3 MB/s of allocation). The check no longer compares the texture names, which come from the same arrays in the same order every time the list is built, and looks up the clamped linear sampler for the overlay and lightmap once instead of once for each.

### Sound channel wait

Every sound the game plays asks the sound thread for an audio channel and waits for the answer on the render thread. The wait parked the render thread, so on top of the sound thread's own wake-up it also had to be woken by the operating system again, 0.3 to 0.5 ms per sound in `/txprofile`. The render thread now spins until the channel arrives and then takes it the same way, so the same channel is used at the same point, without the second wake-up.

### Light snapshots

The light engine keeps one map of light sections it updates and publishes a read-only snapshot of it for every other thread. Every time lighting changed, vanilla published a full copy of the whole map. At render distance 32 that map holds around 100,000 sections, so each copy allocated arrays of several MB on the render thread and on every server worker thread. While moving, `/txprofile` showed most garbage collections forced by these huge arrays, each pausing the game for 8 to 10 ms.

Snapshots are now stored as a tree that each new snapshot shares with the one before it. A chunk column keeps its sections in an array indexed by height, columns are grouped into regions of 16 by 16 chunks, and a small hash map holds the regions. A new snapshot copies that small map, then copies and updates only the regions and columns that contain a section the light engine recorded as changed since the previous snapshot, with that section's current data. Everything else is shared, and nothing in a published snapshot is ever modified, so a thread still reading an older snapshot keeps seeing it unchanged. Every change to the map the light engine updates is recorded that way, so each snapshot holds exactly what a full copy would. There are no full copies anymore, not even periodic ones.

Sky light snapshots also keep each column's top section in the tree. Vanilla copied that whole map of top sections, one entry per loaded chunk column, into every sky light snapshot; it changes only together with a section of the same column, so the tree updates it for the same columns. A lookup now finds the region in the small map and reads the column and the section from arrays, instead of searching the full section map. Vanilla never stores a light section outside the world's height plus one section above and below, and storing one now throws an error instead of being kept silently.

### Sky light lookups

Reading the sky light at a block looked up the column's top section in the snapshot's map of top sections, then the block's own section in the section map, and one more section for every step when it had to walk upward past sections without light data. Chunk meshing reads it for every block it lights, together with the block light. All of these now come from one region of the light snapshot tree: a single lookup in the small region map, then the column's top section and its sections are read from arrays, including the walk upward. The checks run in vanilla's order and return the same light level. Light storages also start with an empty tree snapshot instead of an empty vanilla copy, so every published snapshot is a tree.

### Sky light sources

When a chunk arrives, `ChunkSkyLightSources.fillFrom` finds, for each of its 256 block columns, the highest edge that stops sky light: it walks down from the top filled section block by block and tests every pair of neighbouring states. Each block went through `PalettedContainer.get`, which reads the container's data again and looks the state up in the palette through an interface call, and the edge test also ran for every air block over air. In a server capture with chunks streaming in this scan was 11% of the time inside the slowest 1% of frames. The scan now reads each section's palette data once per column and only looks a state up when the palette id changes from the block above. It also skips the edge test when both states are the one state already found not to occlude itself, since the test only depends on the two states. The same states are visited in the same order and every other pair is still tested, so every column gets the same height.

A chunk that arrives from the server also no longer fills this table at once. When the client enables the chunk's light, the only value its light engine reads is the highest of the 256 heights, and that is now found by scanning down one 16 by 16 layer at a time and stopping at the first layer where any column has an edge that stops sky light, which is exactly the highest entry the full table would hold. The table itself is filled from the chunk's blocks the first time anything reads a column or a block change updates it. Filling it then gives the same heights as filling it on arrival and updating it for every change in between, since each update keeps the table equal to a full fill of the current blocks. A test build that kept vanilla's eagerly filled table next to the deferred one, applied every block update to both and compared every column and every read found no difference over 10,990 chunk loads, 215,658 reads and 43,140 updates, and only 212 of those chunks ever needed the full table. The sky light source work per arriving chunk went from 16.0 to 8.9 microseconds.

### Light writes

Every light level the light engine writes while spreading light (the blocks around a placed torch, or the sky and block light of a newly generated chunk in singleplayer) did two hash set insertions: one marking its light section as changed since the last snapshot, and one marking the section for a mesh rebuild, plus the neighboring sections when the block sits on the section's edge. Light spreads to a block's six neighbors one after another, so consecutive writes are often in the same section. Both insertions are now skipped when the section is the one the previous write already inserted. A block on a section's edge still inserts all of its neighboring sections every time. A section only leaves these sets when the light engine publishes a snapshot and empties them, which also forgets the remembered section, so the sets end up with the same contents in the same order. The neighboring sections are also inserted directly instead of through a new callback object per write.

### Queued light data

Light data from the server (or from disk in singleplayer) waits in a queue until its section is part of the light engine. Every light update that follows new light data or a loaded or unloaded section walked the whole queue to find the sections that became ready. The queue is a synchronized wrapper around a hash map, so the walk went through the wrapper's general iterator, which creates a new entry object for every queued section. The walk now uses the wrapped map's own fast iterator, which reuses one entry object. Both iterators visit the same entries in the same order and remove them the same way, and vanilla's walk did not hold the wrapper's lock either.

### Entity hitboxes

With hitboxes shown (F3+B), every visible entity built its boxes and its view arrow from temporary vectors every frame: an offset vector, the moved bounding box computed twice for living entities, a new stroke style per box, and a scaled view vector. Each arrow then built a rotation, five vectors and an array to draw its four tips. The hitbox boxes now share one immutable stroke style per color, the moved bounding box is computed once from the offset's components, and the arrow end is computed from the view vector's components, all with the same arithmetic as before. Arrows rotate their tips with one reused rotation and write the lines straight into the packed line list. The rotation's terms and its one division are worked out once per arrow instead of once per tip, and each tip is rotated with the same `Math.fma` calls JOML uses, so the GPU receives identical lines. The replaced hitbox method is applied before other mods' mixins and still reads the entity's own box with its first `getBoundingBox()` call, so mods that change that box, such as Meteor Client, still apply.

The four tip offsets of an arrow only depend on the difference between its start and end, and that difference stays the same from frame to frame for every entity that keeps its position relative to its eyes and its view angles. Normalizing the direction, building the rotation and rotating the tips took 2.07% of the render thread in a CubeCraft lobby with hitboxes shown. The tips are now kept in a table of 1,024 entries (about 75 KB) together with the exact bits of the three differences they were worked out from, and an arrow whose differences match its entry's bits reuses the stored tips; any other arrow works them out as before and replaces the entry. Each tip line is still the arrow's end plus its offset, written in the same order. With 600 armor stands and hitboxes shown, the arrows went from 1.73% to 1.27% of the render thread, and the only differing pixels against the old jar were drifting cloud edges.

Each hitbox still made up to five gizmo objects every frame, each wrapped in a collector entry, and the renderer then walked those entries one at a time through an interface call. In a CubeCraft lobby with 467 entities the boxes, points, arrows and their entries were 92 MB/s of the render thread's allocations, and walking the entries took 2.69% of the render thread. The hitbox renderer now records its boxes, points and arrows into one batch, which joins the collector as a single gizmo. A new batch starts whenever any other gizmo was added after the previous one, so all gizmos keep their order. When the batch is emitted, it replays each box, point and arrow through the same emit code the gizmo classes use, with the same coordinates, colors and widths in the same order. A box keeps the coordinates its bounding box object would have held, each minimum being the smaller of the two moved coordinates. A batch is reused once it has been emitted. Hitboxes collected on another thread, or into a collector that is not vanilla's own collector class, still go through the gizmo classes. In a benchmark crowd of 179 entities, three profiles per build put all gizmo work at 7.2% of the render thread before and 3.9% after on average, and the render thread allocated 401 instead of 473 MB/s.

Each hitbox point was still a `Vec3` of the entity's interpolated position and a point record every frame, 14.5 and 11.4 MB/s of the render thread's allocations in a CubeCraft lobby with 447 entities. Gizmo points are now kept as plain numbers like the lines (coordinates, color and size), the hitbox renderer interpolates the position with the same `Mth.lerp` calls `Entity.getPosition` makes, and the point renderer writes the same vertex calls from those numbers. With hitboxes shown, the entity and hologram stations of the benchmark rendered bitwise the same screenshots as the previous build in runs with matching cloud positions.

Each view arrow starts from the entity's view vector, which vanilla works out from its two view angles with four sine and cosine table lookups every time it is asked (0.92% of the render thread with 446 entities and hitboxes shown in a CubeCraft lobby). Each entity now keeps the last angles it was asked about and the vector they gave, and returns that same vector while both angles are bitwise the same. The vector is immutable and depends only on the two angles, so callers get the same values; this keeps one reference and two ints per entity.

### Unused region cache

Every frame, vanilla's level extraction created a new region cache with its own hash map for the visible sections that need rebuilding, although most frames have none. The cache is now created when the first section of the frame asks it for a region, and that one cache serves every later section of the same frame, so every section gets the same region as before.

### Block entity copies of empty chunks

Every section that level extraction sends to be compiled gets a copy of itself and its 26 neighbours, and each of those copies also copied its chunk's block entity map into an immutable map. Most chunks hold no block entities, and Guava still walked an empty map's entries into an array before returning its shared empty map. In the first turn of the motion benchmark 80,358 of 88,077 section copies had no block entities, at about 40 ns each for the copy alone. An empty map now gives Guava's shared empty map directly, the same map the copy returned for it. That made a region copy about 10% cheaper (9.8 µs against 8.8 µs on average in one run each); copying the block states is untouched and remains the largest part.

### GUI texture setups

Every GUI glyph described its textures with a new texture setup record: its glyph texture and sampler plus the lightmap and its sampler. Text in the HUD and menus uses the same few textures over and over, so the last setup is now kept and returned again when the glyph texture, its sampler, the lightmap and the lightmap sampler are all the same objects. The record is immutable, so callers get an equal value either way.

### Default texture matrix

Every entity, item and text render type prepared for a frame asked its texture transform for a texture matrix, and the default transform built a new identity matrix each time (about 12 MB/s of garbage in a BedWars game). The matrix is only read, when the transform is written into the uniform buffer, and vanilla already shares one identity texture matrix for its other transform writes. Render types with the default transform now pass one shared identity matrix, so the same bytes reach the GPU. Glint and offset transforms still build theirs.

### Item frame offset

Every item frame built a new render offset vector twice per frame, once when its entity was placed and once when the frame was drawn (about 5 MB/s of garbage at a spawn full of map frames). The offset only depends on the direction the frame faces, so the six offsets are now built once with the same arithmetic and shared. A vector cannot be changed, so every caller reads the same values.

### Item frame models

Entity render states are created anew for every extracted entity every frame, and every item frame resolved the block model of its wooden border into the new state. With Fabric's renderer that means emitting each quad of the border model into a new mesh, which took 1.6% of the render thread in the benchmark station with 12 item frames. The border only depends on whether the frame glows and whether it shows a map, so there are four possible results. Each one is now built once with vanilla's own `updateForItemFrame` call into a render state of its own, and every item frame of that kind points its render state at the prepared one. Drawing only reads that state, so each frame submits the same mesh as before. The prepared states are dropped when a resource reload replaces the block model set. A model is only shared when it is made of vanilla's classes all the way down: the block model wrapper without tint sources, a single variant and a plain model part over vanilla's quad collection. Those emit the same quads for the same inputs, and an item frame always passes the same fake block state, display context and seed. Border models that a mod replaces with other classes are still built every frame. An in-game check compared the prepared state with a freshly built one, every field and the mesh integer by integer, for more than 368,000 item frame extractions without a difference.

### Entity block models

Block displays, primed TNT, minecart contents, blocks carried by endermen, iron golem flowers, mooshroom mushrooms, snow golem pumpkins, copper golem antennas and sulfur cube contents resolved their block model into their render state every frame, which with Fabric's renderer means emitting every quad of the model into a new mesh. The result only depends on the block state and the display context, since vanilla always uses the same random seed, so each block state is now built once per context with vanilla's own call, and every entity of that kind copies the prepared state into its own: the same model parts, mesh, transformation, render type, tints and light. As for item frames, a model is only shared when it is made of vanilla's classes all the way down (single and weighted variants of plain models, vanilla tint sources), when nothing attached mod data to the prepared state, and when the render state holds no fields beyond vanilla's and Fabric's; anything else is resolved every frame as before. Copying replaces the state's mesh reference after clearing it, as vanilla's update does, so the shared mesh itself is never written again. Prepared states are dropped when a resource reload replaces the block model set. In a TxBench scene with 400 block displays and 40 primed TNT, fps rose from 546, 552 and 639 to 679, 693 and 709, and the displays matched the previous build pixel for pixel.

Fabric's renderer also copies a block model render state's mesh every time the state is drawn, because a state could change after it was drawn. That copy of the 22 border quads was the second largest source of render thread allocations in a profile of the station, about 66 MB/s by the profiler's allocation sampling. The prepared border states never change, so when one is prepared, Fabric's own drawing code is run twice into a recording collector with different light, overlay and outline values, and the mesh copy it submitted is kept together with the render types, parts and tint layers it passed. An item frame is then drawn by submitting the kept copy through the same Fabric call, with the light computed as the larger of the frame's light and the state's block light the way Fabric computes it. The copy is only kept when both recordings saw exactly one block model submission with the unchanged pose, the same render type for every layer, the same parts and tint layers, and the light, overlay and outline values computed that way; otherwise item frames keep drawing through Fabric. An in-game check compared every submission made from a kept copy with what Fabric's drawing code submitted for the same item frame in the same frame, every argument and the mesh integer by integer, for more than 376,000 item frame draws without a difference.

### Entity outline area

Glowing entities are drawn into an outline target of their own, which then goes through four post passes (an edge filter, a horizontal blur, a vertical blur and a copy) before it is blended over the world. Each of those passes and the blend shaded every pixel of the screen, although outlines usually cover a small part of it: with six glowing mobs in the benchmark station they took 0.088 ms of GPU time per frame. They now only shade a rectangle that contains every pixel the outlines can reach.

Each outline draw is marked when it is created, and each outline render type keeps the model-view matrix it was prepared with. When the frame's vertices are handed to the vertex copy thread, that thread also measures the bounding box of the vertex positions of every piece of each outline draw, before it starts on the copies, and the render thread waits for these boxes the same way it waits for the copies, before the first draw and again before the outline pass. When the outline pass starts, the eight corners of each box are projected in double precision with that matrix and the level projection captured for the frame. A triangle that lies in front of the camera only covers pixels inside the projection of its corners, so the union of these screen rectangles holds every pixel the outline pass can write. The union is widened by 2 pixels for the GPU's single-precision rounding, 2 for the edge filter, which reads one pixel to each side, and 4 for the blurs, which read at most three pixels along their axis through bilinear filtering. Every pass of the chain and the final blend draw with this rectangle as their scissor.

The image stays the same. The outline target is cleared before the outline pass, and the chain's intermediate target is cleared whenever a frame takes it from the resource pool, so both hold zero outside the rectangle, which is also what every pass computes there in vanilla, because all its inputs are zero there. Inside the rectangle, each pass only reads pixels that are either inside the rectangle and computed exactly as before, or zero in both cases, so it writes the same values. Blending a zero pixel over the world leaves the world unchanged, so the blend can skip everything outside the rectangle. When the rectangle is empty, the passes and the blend draw nothing.

The rectangle is only used when the post effect file and every shader of the chain, the blend and the outline geometry come from the vanilla resources, the outline pass binds the level projection captured for the frame, and every outline draw uses one of vanilla's two outline pipelines and is drawn by a feature renderer that keeps vanilla's way of drawing its prepared geometry. Otherwise, and whenever a box corner lies behind the camera or within 0.01 of its plane, the passes cover the whole screen as before.

An in-game check alternated frames with and without the rectangle, read the outline target back after the outline pass and after the chain, and compared the final outline images of every two consecutive frames whose outline geometry was identical: more than 6,200 pairs, all bitwise equal. In more than 6,200 frames of that run every lit pixel of the outline geometry lay inside the projected rectangle before widening. In the benchmark station the passes and the blend dropped from 0.088 to 0.028 ms of GPU time per frame. Measuring the boxes on the render thread took about 0.45% of it in that station; on the vertex copy thread, the render thread is left with checking the draws and projecting the boxes, about 0.1%. The same in-game check gave the same rectangle and more than 6,400 bitwise equal pairs with the boxes measured there.

### Outline chain depth

Every post chain creates its intermediate targets with a 32-bit depth texture next to the color texture. The entity outline chain never tests or writes depth, yet its intermediate target's depth texture was cleared every frame when the target was taken from the resource pool and attached to the two passes that draw into it. For the vanilla outline chain the intermediate target is now created without depth, so those passes use the pipeline variant without a depth attachment, which has the same shaders and the same color state. This saves the depth clear and one screen-sized depth texture (8 MB at 1920x1080). With the scissor rectangle and without the depth texture, the passes and the blend took 0.024 ms of GPU time per frame in the benchmark station, against 0.088 ms in vanilla. The same in-game check, now alternating vanilla frames against frames with the scissor rectangle and no intermediate depth, found more than 6,400 pairs with identical outline geometry, all with bitwise equal final outline images.

### Breaking overlay rotation

The block breaking crack overlay computes its texture coordinates per vertex and called `Direction.getRotation()` for every vertex, which allocates a new quaternion and evaluates its sines and cosines (1.3% of the render thread in a CubeCraft lobby). The six rotations are now built once by that same method and reused. The overlay only reads them, so every vertex gets the same values.

### Entity render types

Every model asked its render type function for the render type of its texture once per entity per frame, which looks it up in a concurrent memo map keyed by a `Pair` (0.7% of the render thread with many mobs on screen). Each model now remembers the last texture and the render type it got for it, in one immutable pair, and returns that render type again while the texture is the same object. Vanilla's model render type functions are memoized, so the same texture always gives the same render type.

### Draw group lookup

When an entity asks for a vertex builder, its prepared render type is searched in the current draw group with `List.indexOf`, comparing it with every draw so far (1.5% of the render thread with many different mob textures). Each group now keeps a hash index from prepared render type to its first position, filled when vanilla adds it, so the lookup finds the same draw directly. Groups with up to 8 draws keep vanilla's `indexOf`, which is a few cheap comparisons; a group that grows past that gets a primitive int map built from its list in order, so the first position still wins. The calls are redirected without a wrapper, so adding a draw no longer allocates a boxed position, a map node, an argument array or, for the many small groups, any index at all (an index made for every group was 8.4 MB/s at the LifestealSMP spawn).

### Sky behind terrain

Vanilla draws the sky disc, sunrise glow, sun, moon and stars over the whole screen before any terrain, and the opaque terrain then paints over most of it. In a server lobby these sky passes took 0.019 ms of a 0.131 ms GPU frame. In the overworld with the default transparency, the sky is now drawn right after opaque and cutout terrain and before everything else, with copies of the vanilla sky pipelines whose vertices are placed at the far plane and depth tested against the terrain, so only pixels without terrain are shaded. Terrain does not blend and always writes depth, entities, particles, text, outlines and translucent terrain are still drawn after the sky, and the sky layers keep their order and blending, so the image is the same. The vanilla sky shaders get the far plane line only under a define that just these copies set; if a resource pack replaces one of them and the expected line is missing, the sky is drawn the vanilla way.

The deferred sky used to close the main render pass, open a render pass of its own for the sky and then open a second main pass for the rest of the frame. Every render pass ends with a full GPU barrier that waits for all earlier work, so that was one render pass and two barriers more per frame than vanilla. The sky renderer now draws straight into the main pass, which already has the main color and depth targets it draws into: while the deferred sky is drawn, the render pass it creates is the main pass, which it leaves open, and the frame continues in the same pass. A check throws if the sky ever asks for other targets. The sky renderer binds the same default uniforms and the same fog buffer as the main pass, so every draw after it sees the same values. Over two runs in the copy of the Bedwars prelobby the GPU time per frame went from 52.6 to 41.6 µs and the frame rate from 10,457 to 11,879 fps, and in the singleplayer world from 1,781 to 1,827 fps. The screenshots differed only where runs of the same build also differ: the moving clouds, sections that were still loading and the animated water.

### Startup profile wait

When loading finishes, vanilla builds the screens shown before the title screen and, to decide whether to show a forced name change or banned skin notice, waits on the render thread for the player profile it requested from Mojang's session server at launch. When that server answers slowly, the game stays on the loading screen until the request times out. The check now uses the profile only if it has already arrived and never waits; if it has not, no notice is shown, which is also what vanilla shows once the request fails. The profile still loads in the background and is used everywhere else as before. The account properties request behind the multiplayer ban notice and the title screen's multiplayer button is a different service and is still waited for as in vanilla.

### Shader cache

Every resource reload, including the one when a server sends its resource pack and the one when you leave that server, compiled the shaders of all 385 render pipelines from GLSL to SPIR-V again (the shader loader took 1.7 s of worker time in a CubeCraft reload, including creating the Vulkan pipelines). Each compiled shader is now saved to `txoptimizations/spirv` under a SHA-256 of everything the compiler sees: the shader name, stage, source, defines, every shader include, the compiler flags for the GPU, and the Minecraft and LWJGL versions. The next reload with the same inputs reads the file instead of compiling, so the result is byte for byte what the compiler would produce, and any change to a shader or include compiles it again. Nothing is kept in memory.

### Font provider selection

When a reload finished, the render thread went through every codepoint of every font (more than 60,000 for the unifont alone) in every glyph provider to pick the providers each font uses and to list the glyphs of each width for obfuscated text. That took 72 ms of the 143 ms the render thread was blocked in a CubeCraft resource pack reload. The same work now runs on a worker thread while the reload is still preparing, with the codepoints in the same order, and the render thread only takes the finished result. Instead of asking every provider in turn for every codepoint, it first goes through each provider's list of supported codepoints once and notes the first provider that has each codepoint; bitmap, Unifont, space and TrueType providers return a glyph exactly for the codepoints they list, so that is the provider the old loop stopped at. Fonts with any other kind of provider are worked out the old way.

Before that, vanilla font loading asked every provider of every font for the glyph of every supported codepoint and threw the answers away, so that TrueType fonts load and keep their glyph metrics. Bitmap, Unifont, space and the missing-glyph fallback providers only look the glyph up, so for a font made only of those the loop has no effect, and it took 180 ms of worker time in a CubeCraft reload; it is now skipped for such fonts and runs as before for any font with another kind of provider.

When a resource pack turns font atlas resizing on or off, as CubeCraft's pack does on every join, all fonts are rebuilt so their glyph textures start over, and each font worked out its providers again with the same providers and options, a 138 ms render thread freeze on joining CubeCraft. Each font now keeps the providers and glyph widths it selected last, and reuses them when it is asked again for the same provider list and the same options; anything else is selected as before. It is used only when the font options and every provider are still the same when the reload is applied, otherwise the render thread works it out as before.

A glyph that is drawn for the first time is placed in a font texture by walking that texture's tree of free and used rectangles depth first, and every full texture is walked completely before the next one is tried. With 1024x1024 font textures the trees are 16 times larger than vanilla's, and the slowest frame of a server lobby profile, 3.5 ms, was sampled inside this walk. Each tree node now keeps a bound on the widest and the tallest free rectangle below it, each as the number of bits of the size, in one byte that fits the padding the node object already has, so no node grows. The walk skips a node whose bound shows the glyph cannot fit, which is exactly where the full walk would come back empty, so every glyph lands in the same place, and a full texture is passed over at its root.

### Audio device on reload

Every resource reload closed the OpenAL audio device and opened it again, which took 52 ms of the 101 ms the render thread was blocked in a CubeCraft resource pack reload. The reload still stops every sound, frees every sound buffer and channel and loads the sounds again, but the device and its context stay open when the reopen would pick the same device: the sound device option, the directional audio option and the list of system audio devices are unchanged and the device is still connected. If any of them changed, the device is closed and opened as before.

### Shaders compiled on first use

A reload compiles every pipeline Minecraft registers while it prepares, but pipelines that mods create themselves, like TxOptimizations' own HUD and sky pipelines, were only compiled the first time they were drawn after the reload, and the render thread waited for them. A reload now also compiles, while it prepares, every pipeline that was compiled on first use since the last reload, with the same shaders, and adds it to the new pipeline cache. A pipeline that fails to compile is left out and compiled on first use as before.

### Language files on reload

The language reload read and parsed every language file on the render thread, about 9 ms in a CubeCraft reload. The files are now read and parsed while the reload prepares, and the render thread uses the result when the language and its fallback are still the same; if the language was changed during the reload, it reads the files as before.

### Uniform slots on pipeline changes

When a render pass switches pipeline, the Vulkan backend empties its uniform slot list and then sizes it for the new pipeline, writing every old slot to empty and then every new slot to empty again. It now empties the slots both pipelines share once and lets the resize empty the rest, which leaves the same list of empty slots.

### Atlas upload views

To put each texture into its atlas, a reload uploads it to its own small GPU texture and draws that into the atlas once for every mipmap level. It created a new view of the whole small texture for every level, five identical views per texture with 4 mipmap levels, and creating views was the largest part of the 92 ms reload frame on CubeCraft. Each small texture now gets one view that is used for every level, which is the same view the draws sampled before.

### Shader module cleanup

After a pipeline is built, each of its compiled shader modules frees its SPIR-V and destroys the SPIRV-Cross context that read its inputs and bindings. Destroying those contexts frees thousands of small native allocations, and with every reload worker doing it at once it took 424 ms of the 2,275 ms of worker time in a CubeCraft reload, more than any loading step. Modules are now closed in the same way on one background thread, so the reload workers go straight on to the next task; nothing uses a module after it is closed.

### Unifont reuse

Every reload unzipped and parsed the three Unifont files, more than 60,000 glyph lines read byte by byte, and font loading finished last in a CubeCraft reload because of it. The parsed font is never changed after loading and closing it does nothing, so a reload now reuses the one from the previous reload when the file's bytes have the same SHA-256 and the size overrides are equal; any other file is parsed as before. Only the fonts loaded by the latest reload are kept, and they are the ones the game is already using.

### Duplicate sprite warnings

To draw chests, shulker boxes, banners, decorated pots and bells in the chunk mesh, the mod adds their textures to the blocks atlas, and vanilla keeps them in their own atlases too, so every reload logged about 110 "Duplicate sprite" warnings on the render thread. The warning is no longer written for textures in the folders the mod's `assets/minecraft/atlases/blocks.json` adds when one of the two atlases is the blocks atlas; any other duplicate is logged as before.

### Missing texture warnings

Model loading is the last part of a reload to finish, and its final step wrote a warning for every model with a missing texture, one after another on one thread, to the console and to latest.log. CubeCraft's resource pack has about 1,360 such models, so that step held up the end of every reload with its pack. The same warnings are now written by a background thread after the models are done, in the same order and with the same text.

### GPU memory freed in the background

Vulkan resources that are closed are destroyed two frames later, once the GPU is done with them, and that destruction ran on the render thread. Destroying many at once stalls the frame: after a resource reload with Sodium, which closed the buffers of every loaded chunk region, it took 17 ms of a 33 ms frame on CubeCraft. Buffers, textures and texture views are now destroyed on a single background thread in the same order, at the same point after the GPU finished with them; the GPU memory allocator is internally synchronized, so this is safe. Other resources are destroyed on the render thread as before, and the game waits for the background thread before it shuts the GPU device down.

### First inventory open

The first time the inventory opened in a session, the game loaded about 30 classes it had not needed yet (the recipe book, the creative screen it checks for, the player preview and their Fabric hooks), and every mod's mixins were applied to each one on the render thread right as E was pressed. In survival that made the first open take 12.9 to 14.4 ms against 0.5 ms afterwards. Once the game finishes loading, a background thread now loads those classes without running their setup code, so the first open took 4.4 ms in the same test; what is left is the setup code and lambdas, which can only be made when they are first used.

### Data fixers and crash report preload at startup

Before registering blocks, the game builds its data fixers (the rules that upgrade old worlds and settings) and fills a throwaway crash report so the crash report code is loaded in advance, which includes reading the PC's hardware details. Both ran on the main thread and held up everything after them. They now run on two background threads while the blocks register; the game still waits for the data fixers at the same point as before, just before it opens the window, and the memory kept in reserve for out-of-memory crashes is still set aside on the main thread first. Measured over 5 startups each, with the same startup cache as the launcher, time from process start to the title screen went from a median of 4,528 ms to 4,137 ms.

### Block state cache at startup

Every launch, vanilla builds the shape and lighting cache of all 35,723 block states one after another on the main thread, which took 840 ms in a test run. The states are still registered in the same order, but their caches are now built on all cores right after the block classes finish loading, before anything reads them; in the same test it took 517 ms. Building them inside the block class setup deadlocks, because copper and flower pot blocks read other blocks while their cache is built, so the build waits until that setup is done. A check that rebuilt all 35,723 caches one at a time afterwards found no difference in any cached value.

### Section buffer lookups

Every frame, vanilla asks the vertex and index uber buffers of each terrain layer where every visible section's mesh is stored, and each buffer answers from a hash map keyed by the mesh. Averaged over 8 benchmark scenes, these lookups took 23% of the render thread. Each compiled mesh now keeps its six allocations (vertex and index for each layer) in a small array, and the uber buffers' map calls read and write that array instead: when an upload stores an allocation, when one is looked up or freed, and when a buffer closes. Each buffer also keeps the set of meshes that hold one of its allocations, so closing it clears exactly the entries the map clear dropped. Vanilla only allocates buffer space for compiled meshes, so the placeholder meshes of empty and unbuilt sections still have none. Every lookup returns the same allocation object the map returned, so the draws use the same buffers and offsets. Memory stays about the same, since each mesh gains a six-slot array and each allocation loses its hash map entry.

### Staging buffer waits

A section compile or translucent resort copies its finished mesh into the shared staging buffer under the section dispatcher's lock, and when the buffer is full vanilla's worker spins straight back into the lock, again and again, until the render thread's next upload frees space. While chunks stream in, every chunk worker can be spinning at once, each taking and releasing the lock many times per microsecond. The render thread also took that lock to collect the frame's terrain draws, and in a server profile it waited 6.2 ms for it in one frame; the spinning workers also kept every core busy, and another frame lost 7.5 ms with the render thread just releasing that lock. A worker that finds the buffer full now parks for 50 µs before it tries again. Space only frees when the render thread uploads, once per frame, so the meshes are stored in the same order and only the empty retries are gone.

### Section compile queue

Sections to compile wait in one list guarded by one monitor. Every chunk worker that looks for its next task holds that monitor while it walks the whole list, measuring each task's distance to the camera and removing cancelled tasks one by one, each removal shifting the rest of the list; while chunks stream in the list holds thousands of tasks and the workers poll back to back. The render thread adds every new task under the same monitor, and in a server profile it waited 6.75 ms for it in one frame. New tasks now go into a lock-free inbox that the next poll moves onto the end of the list in the order they were added, before it looks for a task, so the render thread never waits. The poll removes cancelled tasks in one pass that keeps the order of the rest, then picks the nearest new compile and the nearest recompile with vanilla's comparisons and quota, so every worker gets the same task it would have got.

### Section mesh releases

A finished compile with nothing to draw swaps in its new mesh and then frees the old mesh's buffer space, and a cancelled compile frees the space of the mesh it was building. Vanilla's worker did both under the section dispatcher's lock, which the render thread held while it collected the frame's terrain draws, since freeing changes what that collection reads. In a server profile the render thread waited 4.4 ms for this lock in one frame while chunks streamed in, most likely for a worker that the system paused while it held it. Workers now hand these releases to the render thread, which runs them under the lock at the start of its next upload, before that upload hands out any buffer space, so freed space is reused by the same upload as before. The old mesh is already swapped out when it is handed over and a cancelled mesh is never shown, so no mesh is drawn after it is released. Every change to what the draw collection reads now happens on the render thread, so the collection no longer takes the lock at all. The upload still takes it, since workers write their meshes into the same staging buffer.

### Section draw extraction

`LevelRenderer.extractSectionDrawGroups` builds the frame's terrain draw list. For every visible section and every layer it asked the mesh's enum map for the layer's draw, looked up the section's buffers even for layers without geometry and for the placeholder meshes of empty and unbuilt sections, wrapped them in a new slice record, read the vertex size through the pipeline's vertex format list and divided both buffer offsets with 64-bit division. Averaged over 8 benchmark scenes this was 12.9% of the render thread in the method itself, 3.7% in the enum map and 0.7% in the vertex format lookups. Placeholder meshes are now skipped at once, since only compiled meshes ever hold buffer space.

Each compiled mesh with geometry keeps everything a frame needs from it in one int array, its draw record: which layers it has and which of them can be drawn, the six float bounds of its face direction box, and for every layer the id of its vertex buffer, its first vertex and its index count, plus the 21 face direction ints of a solid or cutout layer, or whether a translucent layer has its own index buffer, its index type, the id of that buffer and its first index. A frame reads the record and nothing else of the mesh: no allocation, allocation block or heap, draw map, draw record, facing array or box. GPU buffers are named by small ids: every uber buffer heap registers its buffer when it is made and releases the id when vanilla closes the buffer, which it only does for a heap without allocations, so no record still names a released id. The first vertex and index are divided out with 32-bit division by the layer's vertex size or the draw's index size, which gives the same quotient because an uber buffer heap's size is an int, so every offset fits in one, and the vertex size comes from the same pipeline as before, whose vertex format never changes. The drawable layers, buffer ids and first vertices and indices are worked out again whenever one of the mesh's allocations is stored, freed or dropped with its buffer, and when the mesh is closed and its draws are emptied, so they always match what the allocations and draws give, and all of those changes happen on the render thread, which also runs the draw extraction (see section mesh releases).

The visible sections are walked in chunks of 64. For each chunk the mesh and record of every section are read first, then the first word, position and fade of every section that has something to draw, and only then are that chunk's draws built in visible order. The reads of one chunk don't depend on each other, so their cache misses overlap instead of each section waiting for its own between the draw work of the sections before it. Everything read is either only changed by the render thread or read once per section as before, so the draws, their order and every value are the same. The runs of visible face direction groups that become draws come from a table of 128 entries indexed by the groups that are skipped, which gives the same runs as walking the groups one by one. The mesh itself is no longer read on the way: each section keeps the draw record of its current mesh, and whether that mesh has translucent geometry, in two volatile fields, read again at the end of every mesh swap and reset until the mesh read is still the current one. Meshes are only closed after they were swapped out, so both always describe the current mesh. Collecting the draws then loads the record straight from the section instead of going through the section's atomic reference and the mesh, and the translucent resort check skips sections without translucent geometry without loading their mesh. In the scene with every block, entity and particle type, terrain draw collection went from 20.9 to 16.3% of the render thread (25.4 to 20.5% with ticks frozen) and resort scheduling from 1.6 to 0.7%.

The profiler counts the frame's terrain draws and triangles from the finished list once per frame instead of once per draw.

The draw commands used to be kept as one linked list per draw group and written to the GPU command buffer one int at a time, group by group, with translucent groups written back to front. When the list is finished, each draw now gets its final slot in that buffer (groups in output order, a translucent group's first draw in its last slot), and the draws are moved into those slots inside the same array, in the exact layout of the GPU commands. Writing the frame's commands is then a single copy of the array. Over 200,000 random draw lists the array held exactly the ints the old writer produced, and each group's draw list and the profiler counts were unchanged. In the singleplayer benchmark world this was 1,736 against 1,659 fps over two rounds each, and the same in the lobby copy (12,219 against 12,187) and the entity hub (10,592 against 10,631).

The per-section part of the face direction test described under Terrain face directions is worked out when a section reaches its first solid or cutout layer that can be drawn, and not at all for sections with only translucent geometry or nothing to draw. It depends only on the section's box, its position and the frame, and only the solid and cutout layers of the same section read it, so every face direction decision is the same as when it is worked out for every section. The box's center and half size are computed again from the float bounds with the same double operations that used to build the stored box, so they are the same doubles. The section infos, the draw groups and their order, the hash that merges draws into groups and every draw command are built exactly as before, apart from the split of solid and cutout draws by face direction.

An offline check built the same random sections both ways, the previous mesh arrays and draw loop on one side and the draw records and chunked walk on the other, from the same quads through the real face direction grouping, and ran 6,000 frames with the game's reversed depth projection. Every per-section value of the face direction test was the same double, bit for bit, in all 289,760 sections that could skip groups, all 7,267,181 per-layer decisions matched (524,566 of them on such sections, skipping 1,327,417 groups), and the command bytes, section infos, groups and records matched in every frame (8,631,127 commands). Every one of the 2,187 combinations of empty, drawn and skipped groups produced the same runs. In a synthetic model of 40,000 visible sections with the game's object layout and allocation order, in random visible order, the draw list took 84 to 93 ns per visible section with the previous code and 40 to 41 ns now, and 126 to 136 ns against 78 to 89 ns when the caches are flushed between frames.

Memory goes down for every compiled mesh. The mesh object itself shrinks from 80 to 64 bytes, and its draw record (48 bytes for translucent geometry alone, 144 for one solid or cutout layer, 240 for both, 168 and 264 with translucent geometry added) replaces three slot arrays (112 bytes), the facing arrays (32 bytes plus 104 per solid or cutout layer) and the box (64 bytes), 112 to 192 bytes less per mesh than before. Against vanilla, whose mesh is 48 bytes plus 240 bytes of upload flag maps plus a 32 byte hash map node for each of its buffer allocations, every kind of compiled mesh is now smaller; one with solid and cutout geometry, the closest case, by 3 to 13 bytes depending on the hash map's fill.

### Section draw commands

Every frame the terrain draw list was made of one `IndexedDraw` record per draw (five ints) and one `ChunkSectionInfo` record per section (a position and a fade value), kept in a new list per draw group, a new list of section infos and a new hash map from group hash to group. The indirect draw path then walked every group's list again, translucent ones through reversed list views, and wrote every record through a virtual call that positioned the buffer and stored its values with `ByteBuffer.putInt`. In a profile over 8 benchmark scenes, taken before terrain face directions split solid and cutout layers into up to three draws per section, writing the commands took 4.0% of the render thread, the reversed views 0.7% and the section infos 0.6%.

Draws now go into one int array that is kept from frame to frame, five ints per draw: the four values that vary and the position of the group's next draw, so each group's draws form a chain in the order they were added. Section infos go into a second kept array, four ints each, with the fade value stored by its raw bits. Groups are found through a small kept int hash map with the same keys vanilla's map used, every new group is put into it just as before, and translucent sections still continue the last translucent group while their hash stays the same, so every draw lands in the same group as before, even when two buffers' hashes collide. The commands are then stored with `MemoryUtil` straight into the mapped command buffer, one group after another in vanilla's order, each group's draws in the order they were added; when the translucent order is respected, translucent groups and the draws inside them are written backwards, which is the order vanilla's reversed views produced. The command buffer's capacity check, growth and log message, the buffer slice of each group, and the last written command it remembers are the same as in vanilla's batched write. The section infos are copied in one bulk copy into the staging memory of the section info buffer, which then uploads them with the same buffer write as before.

The arrays start with room for 4,096 draws and sections, double when a frame needs more and keep their size, so they hold at most twice the largest frame so far at 20 bytes per draw and 16 per section, where vanilla allocated a 32 byte record per draw and per section and the lists holding them every frame and dropped them again. The separate draw path used without multi-draw indirect still receives vanilla's group lists and records, built from the same arrays in the same order. Nothing in the game writes `IndexedDraw` records any more, so their write method is no longer replaced. Section infos written for the separate path still store their values with `MemoryUtil` at the same offsets as `Std140Builder` and move the position past them; the bytes are identical, since floats are stored by their raw bits like `putFloat`.

An offline check ran the previous builder, with vanilla's list batching and vanilla's record writes, and the new one on the same 6,000 random frames of up to 2,500 sections each, with both translucent orders, vertex buffers whose hashes collide across layers, translucent groups whose hash equals a solid group's and a translucent hash of 0. The command bytes, section info bytes, group order, group buffers and slices, last command, largest shared index count and the separate path's groups and records were identical in every frame (8,762,886 commands and 3,128,752 section infos), and every frame the old builder threw on also threw in the new one.

Vanilla uploads the per-section instance data of the indirect terrain draws through a staging copy: the bytes are written into CPU memory, then a GPU copy moves them into the vertex buffer, followed by a full barrier that waits for all earlier GPU work. The section infos now go into a ring of mappable buffers, like the draw commands next to them, and are written straight into the buffer the draws read, so the copy and its barrier are gone. The ring only reuses a buffer once the GPU has finished the frame that read it, and the bytes and their offsets are the same. Over two runs in the copy of the Bedwars prelobby the GPU time per frame went from 41.4 to 39.3 µs and the frame rate from 11,883 to 12,264 fps, faster in every run of every view.

### Section upload flags

Every compiled section mesh remembered which of its vertex and index buffers have been uploaded in two enum maps holding one `AtomicBoolean` per layer: two maps, their value arrays and six atomic booleans, 240 bytes per mesh, allocated again for every section that compiles. The six flags are now bits of one `AtomicInteger` (16 bytes) and the maps are no longer made. Setting a flag sets its bit with an atomic update, and reading one reads the integer with the same volatile semantics as the atomic booleans. Closing a mesh emptied both maps, so any later read or write of a flag threw a `NullPointerException`; closing now sets a closed bit, and a later read or write throws the same exception, which matters because the section compile tasks catch exactly that exception and queue the task again.

### Section neighbor checks

Each frame, every visible section that needs a rebuild but was never compiled is only queued once the eight chunks around it are loaded and lit, which vanilla checks with up to eight chunk lookups and light column lookups for every such section in every frame. When a server sends fewer chunks than the render distance, the sections at the edge of what it sent never get their neighbors and are checked again in every frame: in a PvP arena with 14 players that was 2.41% of the render thread, and 0.4 to 0.7% in a server's overworld. The answer only changes when a chunk is added to or removed from the client chunk storage, when that storage is created or moves its center, or when a column of the client's light engine is lit or unlit, so a counter goes up whenever one of these happens. A section whose neighbors were missing remembers its position and the counter, and while both are unchanged it is not checked again. The section still waits for exactly the same neighbors and is queued in the same frame. A light engine other than vanilla's own, such as a Starlight fork, decides whether a column is lit from its own state, so with one installed every section is checked every frame as before. A test build that also ran vanilla's check for every remembered result found no difference in about 380,000 skipped checks while a singleplayer world loaded and played, with about 16,800 changes to the counter.

### Section grid lookups

Finding the render section or the update state of a section position goes through a rotating grid around the camera. Every lookup read the grid's center through its `SectionPos` object four times to check that the position is inside, and then found the grid slot with two `Math.floorMod` calls, each an integer division by the grid width. Entity extraction does such a lookup for every entity its renderer would draw, and the occlusion graph for the sections it walks; averaged over 8 benchmark scenes the lookup took 0.86% of the render thread. Each grid now keeps the bounds of its window and the slot of the window's first column and row in one immutable record, made again only when the grid moves to a new center. A lookup reads that record once, compares against the same bounds vanilla computes (with the same int overflow while the grid has no center yet, so nothing is inside), and finds the slot by adding the offset from the window's edge to the first slot and subtracting the width once if it passes the end, which is the same remainder for every position inside the window. An offline check compared both lookups on 4 million positions around random centers, including the initial center and centers near the int limits, and every result was identical. Other threads see either the old window or the new one as a whole, never a mix.

### Section grid recentering

When the camera enters a new chunk section, both rotating grids around it, render sections and section update states with 101,400 slots each at render distance 32, are moved to the new center. Vanilla went through every slot, read its value and compared its position with the one the slot should hold now, although only the slots of the columns and rows that leave the window change, and none at all when the camera only moves up or down. Every recentering leaves each slot holding exactly the position the window assigns to it, so a slot whose column and row both stay inside the window already holds its new position. Recentering now visits only the slots whose column or row changed, in vanilla's order, checks that each still holds its position in the old window and fails loudly if not, and moves it exactly as before. The first placement of a grid and jumps of a whole grid width or more still go through every slot. While flying in the motion benchmark one recentering took 1.2 to 1.3 ms on average before and 0.24 ms now: 0.35 ms for the render section grid, whose moved sections also release their meshes, and 0.14 ms for the update grid. The column positions are stepped by one and wrapped at the edge of the window instead of each taking an integer division, so a recenter does two divisions per axis instead of about 17,000; on 200,000 random grids the stepped positions matched the divisions.

### Visible section walk

Level extraction rebuilds the list of visible chunk sections whenever the camera turns into a new two-degree step or the occlusion graph adds a section inside the view. In the first turn of the motion benchmark that happened 891 times in 3,000 frames, mostly because newly compiled sections let the graph reach further. Vanilla walks the section octree with a visitor that is called for every branch and leaf it reaches and asks each node for its section, and every leaf fetches its section's bounding box, twice when it is tested. The walk now goes through the octree's branches itself. Leaves under a branch that lies entirely inside the frustum and is not near the camera add their section without reading it; every other branch and leaf is classified with the same frustum calls and the same nearby test in double precision, in the same order, so the visible list, its order and the nearby list are the same. One rebuild took 80 µs before and 64 µs now in the first turn, 61 against 52 µs in later turns and 115 against 102 µs while flying.

An offline check recorded 176 octrees and frustums from the motion and static benchmarks and rebuilt them from vanilla's own classes; vanilla's walk reproduced every recorded list, and the walk in its final form (see Octree leaf sections) returned the same sections in the same order for all of them, as well as for 20,000 random frustums over 1,000 random octrees, some with sections moved after they were added. A verification build of an earlier version ran vanilla's own walk next to it for all 2,225 rebuilds of a motion benchmark run, and one of the final version compared the walk with the octree's own visit for all 2,182 rebuilds of a motion run and 1,236 of a static run; none differed. Rebuilds during which a finished full graph update replaced the octree are not compared, since the two walks would see different octrees.

The walk uses the same frustum as vanilla, a copy of the view frustum moved back far enough to hold the 8 block cube around the camera. The visible list is only rebuilt when the camera turns past a two-degree step or the occlusion graph changes, not when the camera moves inside its section, and the moved-back frustum is what keeps the sections beside and behind the camera in the list when the camera then moves back. An earlier version walked with the view frustum itself to draw fewer sections, which let terrain pop in while walking backwards.

Vanilla's octree visits each branch's children nearest octant first, but it finishes a whole branch before the next, so a far section of a near branch is drawn before a near section of the next branch. Opaque terrain then shades pixels that nearer faces drawn later cover again: in a server lobby our solid terrain shaded 3.05 million fragments per frame against Sodium's 2.72 million for the same triangles. After the walk the visible list is now sorted by the squared distance of each section from the camera's section with a counting sort, nearest first, which is the order Sodium draws in; translucent terrain, drawn from the same list in reverse, gets the matching far-to-near order. The sort moves the sections inside the list's own array, following each section's counting-sort slot, so no copy of the list is made.

### Octree leaf sections

Vanilla's section octree wraps every section it holds in a small leaf object, so the visible section walk still loaded one object per visible section, a leaf in the walk above or, once leaves were gone, the section itself just to check its type. The octree's leaf slots now hold the render section itself. Sections are added exactly as before and each lands in the slot its leaf would have taken, and a branch visits its sections with vanilla's leaf logic, so other users of the octree, such as its debug renderer, see the same nodes in the same order, with the section itself as the node and the same section and box. Whether a branch holds sections or branches follows from its size, as it does when vanilla adds to it, so the walk adds the sections of a fully visible branch that is not near the camera straight from the branch's slots without loading them. Sections it does test take their box from the section's position, which is what their bounding box is built from whenever they move, so the frustum and nearby tests get the same numbers without reading the box. Every full occlusion graph update builds a new octree, which now allocates one object less per section. One rebuild now takes 54 µs in the first turn of the motion benchmark (64 µs with the walk above alone, 80 µs in vanilla), 45 µs in later turns (52, 61) and 76 µs while flying (102, 115).

For the offline check the sections were placed straight into the slots, as the game now does, and the walk was compared with vanilla's walk over the same octrees with leaf objects.

### Translucent resort checks

After every frame, vanilla decides for every nearby visible section and for an eighth of the other visible sections (at least 15) whether its translucent geometry needs sorting again. For each one it worked out the camera's point of view relative to the section, compared it with the point of view the mesh was last sorted for, and only then checked whether a resort was already scheduled, whether the mesh has translucent geometry at all and whether improved transparency is off. Sections without translucent geometry paid for the point of view comparison too, which reads an object the mesh keeps from its last sort; in a profile over 8 benchmark scenes the mesh lookups of these checks took 0.81% of the render thread and the comparisons 0.34%. The checks now run cheapest first: improved transparency, then the mesh's translucent geometry, then the point of view, then the scheduled resort. Whether a mesh has translucent geometry was a lookup in its draw map (0.42% of the render thread in a later profile, plus 0.30% in the check itself); it is now a flag on the mesh, set when the mesh is built and cleared when it is closed, the only two places its draw map changes, and it takes no extra memory because it fits the object's existing padding. Every check only reads state, so a section is resorted in exactly the same cases as before, and the mesh is read once for both of its checks instead of twice.

### Water back faces

Vanilla draws open water from both sides: right after a water surface or side face it writes the same four vertices again in reverse order, and the GPU's back face culling drops whichever of the two faces away from the camera. Both copies still went through vertex fetch and the vertex shader, and both took space in the section's vertex buffer. When a translucent section mesh is sorted for the first time, every quad whose four vertices are a byte-for-byte reversed copy of the quad directly before it is now dropped from the vertex data, and the quad before it is marked as having a twin. Each sort still writes six indices for the twin, right after its original's six, pointing at the original's vertices in reverse order (0, 3, 2, 2, 1, 0), which are exactly the triangles the copy's own vertices gave. Vanilla's order puts the twin directly after its original every time: a quad's sort position comes from the center of its first and third vertex, which the twin shares bit for bit, and the stable distance sort keeps equal distances in vertex order, so no other quad can come between them. The remaining quads keep their order among themselves, so the index buffer has the same length, the same triangles in the same order and the same vertex values, and vanilla's terrain vertex shader reads nothing but the vertex attributes and the section data. A resource pack whose terrain vertex shader reads `gl_VertexID` would see the original's vertex numbers for the shared copies; no vanilla terrain shader or include reads it. Twins are found by comparing the actual bytes, so a copy made by anything other than the fluid renderer is only shared when it is exact, and meshes without twins are sorted as before. The sorted indices of terrain are now written straight to memory instead of through vanilla's index writer lambda, with the same values.

Water sections keep about half their translucent vertex data, sort about half the quads on every resort, and the GPU fetches and shades each shared vertex once. In the benchmark world 224,196 of the 829,965 translucent quads (27%) are shared, 25.1 MB less vertex data and 2.7 MB less sort state. Measured with GPU timestamps around every pipeline in two runs per side, the translucent terrain draws went from 0.0306 to 0.0199 ms per frame in the hologram scene, 0.0481 to 0.0349 ms in the terrain scene, 0.0568 to 0.0486 ms at the water pool, 0.0601 to 0.0477 ms in the busiest scene and 0.1190 to 0.1103 ms in the stained glass scene, which has almost no water. Screenshots looking up at the pool's surface from under water, where only the shared copies are drawn, matched the build without this change pixel for pixel. An offline check built 170,000 random meshes with twins, copies that differ in one byte, plain repeats and many equal distances (39.2 million quads, 11.0 million of them shared), sorted them with vanilla's sort on one side and the shared vertices with this mod's sort on the other, and the vertex bytes of the resulting triangle streams matched in every mesh.

### Frozen tick passengers

While ticking is frozen (`/tick freeze`), every frame and every tick asks each entity how many players ride it, to decide whether it still moves smoothly, and the answer always came from a new stream over all of its passengers and their passengers. An entity without passengers now answers 0 straight away, which is the count the empty stream returned. An entity that carries passengers counts them through the same stream as before.

### Section update lookups

Every frame, level extraction looks up the update state of each visible chunk section to find the sections that need a rebuild, and each lookup worked out the section's slot in the update grid with two modulo operations before reading it. The grid of render sections is laid out the same way, so the slot number every render section already carries is now tried first. When the update state in that slot belongs to the same section and the section lies inside the grid, it is exactly the state the full lookup returns; in any other case the full lookup runs as before.

### Section update scan

Every frame, level extraction walked all visible chunk sections and looked up each one's update state to find the few that need a rebuild. The answer for a section only changes when a block or light change marks a clean section dirty, when the update grid or the grid of render sections moves with the camera or is created, or when the list of visible sections is cleared or refilled other than by a rebuild that carries the list over (see Section subsets across rebuilds). Each scan now remembers, in visible order, the sections that were still dirty when it checked them. While none of those changes has happened since, the next scan checks only the remembered sections, with the same checks in the same order; every other visible section was clean or outside the grid at the last scan and still is. Changes are counted when they start and when they end, so a change made by another thread while a scan runs makes the following scan a full one, and any change makes the next scan walk all visible sections as before.

### Block entity sections

Every frame, block entity extraction walked all visible chunk sections and fetched each one's mesh to see whether it holds any block entities, although most sections hold none. A section only gains block entities when a mesh that has some is installed on it after it compiles. Each frame now remembers, in visible order, the sections whose mesh had block entities when it checked them. While no mesh with block entities has been installed and the list of visible sections has not been cleared or refilled since, other than by a rebuild that carries the list over (see Section subsets across rebuilds), the next frame checks only those remembered sections, with the same fade test and extraction in the same order; every other visible section had no block entities at the last check and still has none. Meshes are also installed from the section compile threads, so each install is counted when it starts and when it ends, and a frame that starts while one is still running is followed by a full walk. Any install of a mesh with block entities and any other change to the visible list makes the next frame walk all visible sections as before.

### Section subsets across rebuilds

The section update scan and the block entity scan each remember the visible sections that matter to them, but every rebuild of the visible list threw both lists away, so each rebuild was followed by a walk of all visible sections in both scans. In the first turn of the motion benchmark those two walks took 61 µs and 48 µs per rebuild, more than the rebuild itself. A rebuild now carries both lists over. Every render section keeps one int: the number of the last rebuild that listed it and whether it was in each of the two lists then. After the octree walk, a section that the previous rebuild listed too takes both answers from that int, as long as nothing that could change a scan's answer has happened since that scan's list was made, the same condition under which the scans reuse their lists; every other section, and every section of a scan whose answers may have changed, is checked the way that scan checks it. The new lists keep visible order, so the next scans visit every section that would update or extract anything, in the same order, and do the same work. Scans mark every section they check, so the int always matches the current lists. A clear or refill of the visible list that is not such a rebuild still makes both scans walk everything and the next rebuild check every section. After 2^30 rebuilds every section's int is cleared before the numbers start over. With the JVM's default compact object headers the int fits into padding the render section object already has, so it takes no memory; without them it adds 8 bytes per render section. In the first turn the carry took 18 µs per rebuild.

Verification builds compared, before every scan that reused its list, what the reused list would update or extract with what a walk of all visible sections would, through a motion and a static benchmark run: all 207,972 block entity scans and 207,914 update scans that reused their lists did the same work, and only 26 and 84 scans walked all visible sections.

### Display entity view range

Every frame, each block, item and text display read its view range from its synced entity data to decide whether it is close enough to draw, which goes through the data table, the data entry and a boxed float. The view range only changes through the synced data, and every change to synced data calls the entity's update hook right after the new value is stored, so each display now keeps its view range in a plain field that is read when the display is created and again whenever that hook reports the view range. The distance check uses that field with the same arithmetic, so it gives the same answer.

### Text display line splitter

Every frame, each text display's render state asks the display for its cached line layout and passes vanilla's line splitter, which the display only calls when the layout is not cached yet. The splitter was a new method reference every time, about 14 MB/s of the render thread's allocations in the busiest benchmark station. Each text display renderer now creates that reference once and passes it every frame, so the same method splits the lines whenever a layout is needed.

### Dragon head culling boxes

Every frame, each mob, armor stand and player close enough to be drawn reads the item on its head during its visibility check, because a worn dragon head sticks out of the body and vanilla grows the culling box by half a block for it. That read went through the equipment map, the head stack and the stack's item holder of every one of them, and took 2.2% of the render thread in a profile. Each living entity now keeps its head stack in a field of the entity itself when that stack holds a dragon head, and the empty stack otherwise. Its equipment refreshes that field whenever the head slot is set and whenever all equipment is replaced or cleared, which are the only ways its slots change, and once when the entity is created. Keeping the stack in the equipment object, as an earlier version did, still cost a read of that separate object for every checked entity: 0.55% of the render thread across all benchmark stations and 4.1% in the sky station, where little else is drawn. The culling check runs vanilla's dragon head test on the kept stack. A stack never changes its item, so a head that was not a dragon head cannot become one later, and the test still reads the stack's count, so a dragon head stack that drops to zero stops counting just as before. This keeps one reference per living entity and one per equipment, which points back to its entity.

### Entity flags

Each entity keeps seven on and off states in one byte of its synced entity data: on fire, sneaking, sprinting, swimming, invisible, glowing and gliding. Every read of one of them went through the data table, the data entry and a boxed byte, and entity extraction reads several for every entity it extracts each frame, such as the glow check, the invisibility check and the sneaking check. The glow check of text displays alone took 0.57% of the render thread in a profile. The byte only changes when synced data stores a new value, either set on the entity or received from the server, so each entity now also keeps a plain copy of it, written right after vanilla stores the new value and before any update hook runs. Every read tests the same bit of that copy. The copy starts at 0, the value vanilla defines for the byte, and adds one byte field per entity.

### Custom names

Every frame, the name tag check of each extracted entity within name tag range asks whether its custom name is visible and, when it is not, whether it has a custom name at all, and a name that is shown is then read with `getCustomName`. Both values sit in the synced entity data next to the flag byte and were read the same slow way. In the sky station of the benchmark, which extracts the text displays of the hologram field, `isCustomNameVisible` alone took 2.0% of the render thread. Each entity now keeps plain copies of the visibility flag and the name, written by the same hook as the flag byte right after vanilla stores a new value, and `isCustomNameVisible`, `getCustomName` and `hasCustomName` read the copies. The name copy holds the component inside vanilla's optional, so `getCustomName` returns the same object, and an optional never holds null, so a present name and a non-null copy mean the same thing. The copies start as not visible and no name, the values vanilla defines. An in-game check compared all three answers with the synced data on 28 million calls during a benchmark run without a difference. This adds one reference and one boolean per entity.

### Item layers in render states

Every item render state was created with one item layer, and every layer holds its own transform matrix. Entity render states are created anew for every extracted entity every frame: the state of each living entity has an item state for its head, mobs that hold items add one per hand and players one more, so a player's state alone created four layers and four matrices whether it held anything or not. Creating the hand item states of player states took 0.29% of the render thread in a profile. An item state now creates its first layer when an item model first asks for a layer, which is when vanilla hands out that layer. Vanilla only reads the layers in use, except for the block light flag, which it reads from the first layer even when no layer is in use. For a state that has not created a layer yet, that read returns false, which is what the untouched layer vanilla would have read holds.

### Item model lookups

Every item drawn in a frame looked up its model and its client item properties by identifier in two hash maps (`HashMap.getNode` under `ModelManager.getItemModel` was 0.8 to 1.3% of the render thread in CubeCraft lobby profiles), and the item display pre-cull did the model lookup again. Most stacks use their item's default model identifier, the same object every time, so each item type now keeps the last identifier it was asked for together with the model map it was found in and the result. The kept result is returned only for that same identifier object and that same map, which a resource reload replaces, so the answer is always what the map would give. In a TxBench scene with 400 item displays, `HashMap.getNode` fell from 3.24% to 0.71% of the render thread.

Each new item state still got its own one-slot layer array to hold the layer it no longer created. It now starts with one shared empty array, and the first time an item model asks for layers the array grows into the state's own array, the same size and contents vanilla's would have at that point. Nothing writes into the shared array, since it has no slots, and every read of the layers is limited to the layers in use except the block light flag, which reads false while the state has no layer. Over four profiles of the previous build the empty arrays were 0.47 to 0.91% of the render thread's sampled allocations across the benchmark stations and 0.68 to 3.73% in the entity station, and none were sampled in three profiles of the new one.

### Name tag layouts

Every frame, each entity that shows a name tag builds its name as a new component: `getDisplayName` copies the name and gives it a new style with a hover event and an insertion, and a below-name score gets a new component as well. A new component has no visual-order text yet, so every name tag was reordered for bidirectional text again, and its new character sequence never matched the world text layout cache, which keys layouts by sequence object. Both parts of a see-through name tag were laid out again every frame and stored as two new cache entries that were never read, which filled the cache until it was cleared at 4096 entries, dropping the layouts of text displays and signs with it. In the hologram benchmark station, laying out world text that missed the cache took 1.17% of the render thread. Each entity now remembers the last name tag and score text it handed out, and when the new component is equal to the remembered one by vanilla's `equals` (same contents, style and siblings), the remembered component is handed out instead. Its cached visual-order text then finds the same layout cache entries every frame. Equal components draw the same text, so the output is unchanged. Only components made of literal and translatable text are remembered, because those keep drawing the same characters while they stay equal; a key binding name inside a component follows the key when it is rebound, so such components, and any other kind of content, are never remembered. An offline check built names the way `getDisplayName` and player names do, with styled siblings and translatable arguments, and every equal pair gave the same visual-order characters and styles, while names with different text, style, insertion or click event, and names with key binding names, were not reused. This keeps two references per entity.

### Entity iteration

Entity extraction walks all loaded entities every frame, and the hitbox renderer walks them again when hitboxes are shown. The level hands them out through Guava's unmodifiable iterable, whose iterator forwards each `hasNext` and `next` to the map's value iterator. That forwarding iterator is shared by every unmodifiable Guava iterable in the game, so the JIT sees many iterator types behind it and calls the map's iterator through an interface dispatch instead of inlining it. In a profile the forwarding `next` took 0.50% of the render thread across all benchmark stations and 2.8% in the sky station. The entity lookup now returns its own unmodifiable view of the same values collection. Its iterator forwards to the same value iterator, so it gives the entities in the same order, and throws on `remove` like Guava's; `forEach`, `spliterator` and `toString` go to the collection, exactly as Guava's view does. Only entity lookups use this iterator, so the JIT inlines the map's iterator into each loop. With Guava's forwarding call site made polymorphic as it is in the game, walking 420 entities took 2.4 to 2.9 ns per entity through Guava's view and 1.0 to 1.1 ns through the new one in an offline benchmark, and over random insertions and removals both views gave the same order, `forEach` order, string and spliterator characteristics.

### Item quad loop

Every item drawn in the world walks the quads of its model with a for-each loop. The quad lists are immutable lists made by `List.copyOf`, and their iterator class is shared by every immutable list in the game, so the JIT sees several list classes behind the iterator's `get` and dispatches it through an interface call for every quad instead of inlining it. In a profile the iterator's `next` took 0.85% of the render thread across all benchmark stations and 2.2% in the busiest one, and the list's `get` showed up under it as a separately compiled method instead of inlined code, which is what a polymorphic call looks like rather than a cold list. The main and outline item quad loops now walk the list by index, so the `get` call belongs to the item renderer's own loop, where only the two immutable list classes that hold item quads show up and both get inlined. The loops visit the same quads in the same order and make the same calls in the same order. In an offline benchmark over quad lists built from vanilla's quad and material records, with the shared iterator made polymorphic as it is in the game, a quad took 3.24 ns through the iterator and 1.45 ns by index, and both loops returned the same quads. Over three profiles per side, the time the item loop spends outside vertex writing went from 26.2 to 11.4 µs per frame in the entity station and from 28.5 to 12.7 µs in the busiest one, and the iterator itself from 10.7 and 11.6 µs to 1.3 and 0.3 µs. Consecutive quads of the same render type that merges consecutive geometry still reuse the vertex builder the previous quad got; the reuse is now kept in locals of the loop instead of fields compared with the previous submit, so it never reaches past one item. The replaced method is applied before other mods' mixins and still reads the foil type once through `submit.foilType()`, so mods that change it there, such as Meteor Client's option to hide the enchantment glint, still apply.

### Item side faces

A flat item, such as a held sword, a dropped item or an item in a frame, is its texture's front and back face plus a thin side face along every edge of its opaque pixels, and vanilla bakes one side quad for every pixel that has a transparent neighbor on that side. Side faces are now baked the way Sodium bakes them: the same pixels get side faces, found with vanilla's test over every frame of the texture, and each run of neighboring pixels with a face on the same side becomes one quad, along the row for the top and bottom sides and along the column for the left and right sides. A run's texture coordinates cover its pixels exactly along the run and keep vanilla's inset of a tenth of a pixel across it. The side faces of the second and later layers of an item, such as the overlay of leather armor, are moved outward by 0.005 per layer index, as Sodium moves them, instead of lying exactly on the first layer's side faces. Items therefore look as they do with Sodium, which can differ from vanilla by a fraction of a pixel at the ends of a run and on layered items. The 831 textures in the vanilla `textures/item` folder bake 50,884 side quads in vanilla and 28,898 merged, 42% fewer quads in all once their front and back faces are counted.

### Biome blending

Grass, leaves, water and other tinted blocks get their color from the average over the biome blend area around them, 5 by 5 blocks at the default blend radius of 2. Every block that needed a tint looked up the biome of every block in its area again, and each lookup runs biome zooming and a chunk lookup in the client chunk map. In a profile of the chunk build threads this took 36% of their time, 28% in the chunk lookup alone. Neighboring blocks share almost all of their area, so while a section is meshed, each biome looked up for it is kept in a per-thread grid that covers the section and the blend radius around it, and the averages of all blocks in the section read their biomes from there. The color resolver still runs for every sampled position with the same biome and coordinates, the colors are added in the same order and divided the same way, so every tint is identical. Tints whose blend area reaches outside the grid, tints asked for outside chunk meshing and a blend radius of 0 look their biomes up as before. The grid is emptied after every section, and also in the middle of one whenever a chunk loads, a chunk's biomes change or the tint caches are cleared, which are the moments vanilla throws away its finished tints. A tint stored after that is therefore never averaged from a biome looked up before it, exactly as in vanilla. The grid holds at most 6,400 biome references per meshing thread at radius 2 (14,400 at the maximum radius of 7).

### Tint cache layers

Every tint lookup goes through vanilla's tint cache, which keeps the finished tints of each chunk column in one array per height. Finding that array took the column's read lock and searched the column's heights one by one on every lookup, so meshing threads working in the same column kept writing to the same lock. Each thread now also remembers the arrays it got for up to 16 heights of the column it is in, and only asks the cache again for a height it has not seen there, after it moves to another column, or once vanilla replaced the column's cache. A column's cache never swaps the array of a height it already holds, so the remembered array is the same one the lookup returns, and tints are still computed, stored and read exactly as before.

### Smooth lighting cache

Smooth lighting reads the light level and the shade of the blocks around every face it lights. Vanilla keeps the last 100 of each in two small hash maps per meshing thread, but a section is meshed along x first, then y, then z, so the neighbors one row and one layer away were looked up 16 and 256 blocks earlier and have long been pushed out of those maps when they are needed again. Every miss reads the light engine or the block's shade again and inserts it into the map. In a profile of the chunk build threads, the shade map's lookups and inserts took 3.3% of their time and the light lookup through its map another 6%. While a section is meshed, the light and shade of every position in the section and the one block border around it are now kept in two flat arrays indexed by position (18 x 18 x 18 entries, 23 KB each per meshing thread), filled the first time a position is asked for. Each entry holds exactly what vanilla's maps hold, the sky and block light from the light engine and the shade of that position's block, and the light emission of the block being lit is still applied on every lookup the same way. Positions outside that box and lookups outside chunk meshing still go through vanilla's maps.

### Block states while meshing

Meshing a section reads the same block states over and over: face culling reads all six neighbors of every block, smooth lighting reads up to ten positions for every lit face, and fluids read their neighbors and the blocks above them. Every read goes through the section copy's palette, unpacking a bit-packed index and looking it up in the palette. While a section is meshed, the block states of the section and its one block border are now kept in a per-thread array of 18 x 18 x 18 entries, filled on the first read of each position, and later reads of that position return the stored state. Section copies are snapshots that never change while a section is meshed, so every read returns the same state as before. The meshing loop's own read of each block still goes straight to the section copy, since it reads every position only once, reads from other threads and outside the border do the same, and after the section only the entries that were filled are reset.

### Enclosed fluids

Every block with a fluid in it is handed to the fluid renderer during meshing, including water deep inside an ocean or lake, which has the same fluid on all six sides and draws nothing. Fabric's fluid rendering hooks run each of those calls through their handler chain first: a cancellable callback, the default handler, a scoped value bound around a lambda that calls the fluid renderer a second time, and a second callback, before vanilla reads the six neighbors and returns without drawing a face. Fluid rendering took 22% of the chunk build threads in a profile, every enclosed block included. When no mod has registered its own handler for the fluid, meshing now reads the six neighbors first and skips the call when all of them hold the same fluid, which is exactly when vanilla draws no face. Fluids with any other neighbor, and fluids with a registered handler, go through Fabric's chain as before.

### Terrain face directions

Vanilla draws the solid and the cutout geometry of each section as one range. The terrain pipelines cull back faces, so the GPU drops every face that points away from the camera, but only after it has run the vertex shader on its four vertices and assembled its two triangles. Sodium keeps each section's faces grouped by direction and only draws the groups that can face the camera; vanilla terrain now does the same.

When a section is built, its solid and cutout vertex data is reordered in place right after the mesh is created from the finished buffers, so every quad is included no matter who wrote it, Fabric's renderer and baked block entities included. A quad joins the up, down, north, south, east or west group when the normal from its two diagonals points along that axis within Sodium's tolerance, 0.5/127 on the other two components (the same as Sodium's 8-bit packed normals), so faces of resource pack models that are a hair off the grid are culled as well; everything else goes to an unassigned group that is always drawn. A group's plane is the nearest of its quads' corners. The groups are laid out so that the visible ones form at most three ranges, each section keeps the nearest plane of every group, and a group is skipped when the camera is at least 3 blocks behind that plane, the same margin Sodium uses against the section's bounds. The test is a handful of comparisons per section. Faces seen almost exactly edge-on from behind can differ from vanilla by single pixels, as they do with Sodium. Opaque faces of different directions now draw in a different order, which only matters where two of them have exactly the same depth.

Within each direction group the quads are also ordered by their plane, the one furthest along the group's direction first. A face can only be seen from the side its direction points to, so of two faces of the same direction that cover the same pixel, the one further along that direction is always the nearer one, wherever the camera is. Vanilla meshes blocks in z, y, x order and Sodium in y, z, x order, so both often shade a far wall and then cover it with a nearer wall facing the same way. Planes are compared on a grid of 1/1024 of a block and quads on the same grid plane keep their mesh order, so coplanar quads such as a grass block's side overlay are still drawn after the face they cover. The order is set once when the section is built and costs nothing per frame. With the game's reversed 32-bit float depth, faces that are not coplanar cannot tie in depth within render distance, so every pixel ends up the same. In the copy of the Bedwars prelobby the solid terrain shaded 2.4 to 2.7% fewer fragments in three of four views, fewer than Sodium in all four, and in the singleplayer world 0.8 to 9.0% fewer. Screenshots of the prelobby matched an earlier build bit for bit, and in the singleplayer world every pixel outside water matched apart from sections that were still loading, which also differ between runs of the same build. The water and the underwater plants, whose textures are animated, differed by one or two color steps.

### Terrain vertex attributes

A GPU timing of every pipeline showed that terrain takes 87 to 93% of the main pass, and that the terrain draws stay nearly as slow when no triangle is rasterized at all, so the cost is in fetching and processing vertices, not in pixels. Vanilla stores each terrain vertex in 28 bytes: three floats for the position, the color, two floats for the texture coordinate and two 16-bit light values, plus the section position and fade value as per-section instance data. In the singleplayer view at 0 128 0, solid terrain alone draws 2.04 million triangles from about 4.1 million vertices, 114 MB of vertex data a frame.

Finished section meshes are rewritten on the chunk building threads into 20-byte vertices, after the face direction grouping and the translucent sorting have read the original data: the position as three 20-bit fixed point values covering 8 blocks below to 24 blocks above the section origin in steps of 1/32768 of a block, the color unchanged, each texture coordinate as a fixed point value in steps of 2^-23, and each light value as one byte. The steps are powers of two, so every position on the 1/16 block model grid and every texture coordinate on an atlas texel comes back exactly. Off-grid positions such as water heights and offset plants move by at most 1/65536 of a block, other texture coordinates by at most 2^-24, finer than Sodium's 15-bit texture coordinates, and light and color are exact. Over 4,000,000 random vertices, every grid position, texel coordinate, color and light value came back exactly and the rest stayed within those bounds.

Every terrain pipeline (normal, multi-draw, wireframe and the improved transparency stages) is drawn through a copy that reads the compact data with the patched vanilla terrain vertex shader: the position and the texture and light coordinates are two unsigned integer pairs, and the section position and fade value one four-component integer attribute, decoded back into the values the shader works with. A resource pack that replaces that shader keeps the 28-byte vertices and the vanilla pipelines. When that changes, the section renderer is recreated with the matching vertex size, and terrain is not drawn in the frames before it has been. Reading the same 28 bytes as four attributes instead of six had cut the main pass from 0.525 to 0.462 ms in the terrain scene; with 20-byte vertices, the benchmark's singleplayer far view went from 0.443 to 0.410 ms of GPU time per frame and from 1,770 to 1,935 fps over three runs per build. The lobby, with and without improved transparency, rendered identical pixels below the sky, and in the far view the differences stayed within the run-to-run noise.

### Fully faded-in terrain

Vanilla's terrain shaders fade newly loaded sections in from the fog color. The vertex shader works out a fade value for every vertex from the section's visibility and the vertex's distance, and the fragment shader mixes the fog color into every pixel by that value. A section's visibility is exactly 1 once its fade-in time has passed, and always when the fade-in time is set to 0, so in those frames the fade value is 1 and the mix returns the pixel's own color. When every section drawn in a frame is fully faded in, terrain is now drawn through a second copy of each packed pipeline whose vertex shader sets the fade value to 1 and whose fragment shader skips the mix. The section walk notes whether any drawn section is still fading, and frames with one keep the normal pipelines. A resource pack that replaces the fragment shader keeps its own code, which then mixes by exactly 1, and one whose vertex shader works out the fade value its own way always keeps the normal pipelines. In the benchmark's singleplayer far view this took the GPU time from 0.391 to 0.376 ms per frame and the frame rate from 1,988 to 2,110 fps over four runs per build, faster in every round. The screenshots differed only by drifting cloud edges and sections still loading at the horizon, as two runs of the same build do.

### RGSS texture filtering

With texture filtering set to RGSS, vanilla's terrain fragment shader samples the block texture nine times per pixel: four rotated-grid samples at each of two mip levels plus one nearest sample, and then blends the nearest sample with the rotated-grid average by a factor that is exactly 0 whenever a texel covers at least one screen pixel. In that case the shader now returns the nearest sample right after computing the factor, which is the same result bit for bit, and skips the other eight samples. That is all terrain close enough for its texels to be magnified, roughly everything within about 48 blocks at 1080p, which is most of the screen in lobbies and near the player. For the remaining, minified terrain the rotated-grid average is taken the way Sodium takes it: four samples at the exact mip level, blended between levels by the sampler, instead of four samples at each of the two neighbouring levels blended in the shader. In a server lobby this took solid terrain from 0.075 to 0.039 ms per frame. The include is only changed when it contains vanilla's sampling code, so a resource pack with its own sampling is left alone.

### Memory

Less live memory means shorter and rarer garbage collections.

- Block state neighbor table: instead of every block state holding its own table of neighbor states, all states of a block share one bit-packed table that `setValue` indexes into. `getValue` keeps reading vanilla's per-state value array.
- Block state cache deduplication: identical collision shapes and face sturdiness arrays in the per-state cache are shared instead of stored once per state.
- Empty item component patches: items with no changed components share one empty map instead of each allocating their own.
- Uniform light layers: a 2 KB light array where every value is the same non-zero level (sky sections at full light, sent by the server or loaded from disk) is stored as just that level, the form vanilla already uses for freshly lit sections. Reads return the same value and the array comes back filled on the first write. A heap dump of a 32 chunk singleplayer world had about 14,000 such arrays (29 MB).

## Commands

`/txprofile reload` makes the next resource reload, such as the one after a server sends its resource pack, run with vanilla's reload profiling, which logs to `latest.log` how long the reload took and how long each reload listener spent preparing and applying. `/txprofile` records 10 seconds and saves one report to the `txoptimizations` folder. It starts the Flight Recorder and runs all of its own timing first, for at least one second and until the JIT compiler spends less than 50 ms of every 500 ms (at most 10 seconds, the report's header says which), then waits until those GPU results are read, clears them and measures from the next frame, since starting the recorder stalls a frame for 100 to 300 ms, its class redefinition and burst of compiled code set off a garbage collection that slowed the following half second, and the profiler's own first frame of timing (creating its query pools and compiling its code) took 7.4 ms; in a server lobby profile 7 of the 10 slowest frames fell in that first half second. Flight Recorder events are reported from the start of the measurement, on the same clock as the frames. The report starts with the frame rate from every frame's time: average, 1% low and 0.1% low (the frame rate at the 99th and 99.9th percentile frame time) and the worst frame, followed by GPU command counts per frame (render passes, pipeline sets, draws, multi-draw calls, indirect and batched draws), the scene (server or world, dimension, position, loaded entities and players, particles), whether hitboxes, chunk borders and the F3 overlay are on, the video options, the GPU and driver, the JVM with its collector, heap and launch flags, and the swapchain's format, image count and present mode next to the format of the main framebuffer that is copied into it. Then come frame time percentiles (p50 to p99.9), how many frames took longer than 1, 2, 4, 8 and 16 ms, and the frame count, average frame rate and worst frame of every second. The GPU part lists the time of every render pass and pipeline per frame. It also lists the 10 frames that took the GPU longest, each with its 4 most expensive passes, timed when the frame's results were read. The CPU part samples the render thread's call stack every millisecond and lists every sampled method by its own time (with its top callers), the 30 hottest call stacks up to 12 frames deep, and every method by its time including callees, plus the CPU time of every thread. A separate section covers only the slowest 1% of frames: what the render thread was doing inside them, their 15 hottest call stacks, the 10 worst frames with the samples taken during each, and every garbage collection with its time, length, the old generation's size after it and the used and committed size of all memory pools, marked on any slow frame it overlaps. It also lists how much memory each thread allocated per second and how much the render thread allocates per frame, which is what fills the young generation and sets how often those collections happen. The JDK's built-in Flight Recorder adds JVM events: every safepoint, every VM operation by name (garbage collection, deoptimization, handshakes and others) with the longest ones, every JIT compilation with the longest ones, deoptimizations by method and reason, every time the render thread parked or waited for a lock for 0.2 ms or longer, by call site, every queue submit, present, present thread start after the frame was handed over and batch of background GPU object destroys that took 0.2 ms or longer, with its thread, and every class the render thread loaded for 0.1 ms or longer, with the game code that first used it. Every garbage collection pause is broken down into G1's phases with their times, the slowest worker in each parallel phase (object copy, root scanning, code roots and others), the eden, survivor and old generation sizes before and after it, and how many regions it collected and MB it copied, which shows whether a long young pause comes from surviving objects or from scanning references. It also samples the allocations, listed per thread by class and by allocation site six frames deep. About 10000 samples make one sample roughly 0.01%, so shares below that are not measurable. Sampling another thread's stack briefly pauses it, so the render thread runs a little slower while the profile records. Copy labels are worked out once per buffer and pipeline labels once per pipeline, and the profiler's timestamp queries are reset in one call per frame after reading them instead of one call per query, to keep the profile's own cost low.

## Fixes

### Command suggestion crash

Typing a command in chat updates the usage hint once the suggestions arrive, on whichever thread finished them. Measuring that hint can bake a new font glyph, which records a texture upload into the render thread's command buffer from another thread and crashed the NVIDIA driver. The update now runs on the render thread, and is skipped if newer suggestions replaced it in the meantime.
